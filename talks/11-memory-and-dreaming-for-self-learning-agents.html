Memory กับ dreaming ทำให้ Managed Agents เรียนรู้ข้ามงานได้

Memory and dreaming for self learning agents

ผู้พูด: Ravi (leads the API knowledge team within platform, Anthropic)

เหมาะกับ: คนที่ทำ agent ระยะยาวหรือหลาย agent และอยากให้ agent เรียนรู้จากงานก่อนหน้า ควรรู้จัก Managed Agents ระดับพื้นฐาน

Ravi อธิบายว่า memory ของ Claude Managed Agents ออกแบบเป็น file system ที่หลาย agent แชร์ได้พร้อมสิทธิ์ read-only/read-write และมี version history ส่วน dreaming เป็น batch process นอก session ที่อ่าน transcript ข้าม session แล้วเสนอปรับ memory ให้ถูกต้องและเป็นระเบียบขึ้น ปิด loop ให้ agent เรียนรู้ต่อเนื่อง

Managed Agents memory is a shared, versioned file-system store; dreaming is an out-of-band batch process that reviews session transcripts and curates memory so agents self-improve.

ประเด็นสำคัญ

  1. ภาพรวมเส้นเวลาตามที่ผู้พูดเล่า: MCP (2024), Claude Code กับ Agent SDK (2025), skills ปลายปีนั้น และ Claude Managed Agents เมื่อเดือนก่อน agent ทำงานยาวขึ้นเรื่อยๆ แต่การจัดการ context ในงานยาวยังเป็นงานที่ทำอยู่ memory จึงสำคัญ
  2. เป้าหมายของ memory คือประสิทธิภาพดีขึ้นจาก task หนึ่งไปอีก task, ข้าม environment และข้าม agent เพราะถ้าไม่มี memory ทุก task เริ่มจากกระดานเปล่า
  3. ผู้พูดอ้างผลจากลูกค้า: Rakuten ลด first-pass error ใน production agent ลง 97%, WiseDocs ลดปัญหาซ้ำในงานตรวจเอกสารด้วย cross-session memory
  4. หลักการออกแบบคือ 'get out of Claude's way' โมเดลเก่งกับ file system, bash, grep อยู่แล้ว จึงโมเดล memory เป็นไฟล์ (ต่างจากเดิมที่เป็น capability ใน harness เช่น Claude.md หรือ memory tool) และบอกว่า Opus 4.7 เก่งเรื่อง file-system-based memory
  5. สำหรับหลาย agent: หลาย session แชร์ memory store เดียวกันพร้อมกันได้ มี scope read-only (เช่น memory ระดับองค์กรที่อัปเดตไม่บ่อย) กับ read-write (เฉพาะงาน) เกิดเป็นลำดับชั้น และใช้ optimistic concurrency control กันเขียนทับกัน
  6. ฝั่ง enterprise: version control เป็น audit trail ดู diff ระหว่างเวอร์ชันได้ บอกได้ว่า agent ตัวไหนเขียนส่วนไหน และมี standalone API ทั้ง CRUD และ export กับ redaction
  7. ปัญหาที่เจอเมื่อขยายเป็น multi-agent: agent ทำผิดซ้ำและเรียนรู้แยกกัน ใช้วิธีที่ไม่มีประสิทธิภาพคล้ายกัน memory ถูกอัปเดตแบบ optimal เฉพาะที่ ไม่ optimal ทั้งระบบ เกิดซ้ำซ้อนและกระจัดกระจาย
  8. dreaming (research preview ใช้กับ managed agents) เป็น batch process นอก session แยกจาก agent loop เรียกได้แบบ ad hoc, รายคืน, รายชั่วโมง หรือผูกกับ event เช่นจบ session ผ่าน API มันวิเคราะห์ transcript ตรวจ memory ปัจจุบัน แล้วเสนอ snapshot ใหม่ที่ตรวจแล้วให้ agent เลือกรับ
  9. เหตุผลที่ต้องอยู่นอก hot path: เห็น pattern ข้าม session/agent ที่ agent เดี่ยวมองไม่เห็น, มี objective ชัดไม่ต้องแลก memory quality กับการทำงานให้เสร็จ, และไม่เพิ่ม latency ให้ agent
  10. เดโม SRE: agent triage alert อ่าน memory org-wide แบบ read-only (SLO policy, runbook, on-call mapping) และเขียน memory เฉพาะงาน session ถัดมาเห็นว่ามี fix กำลังไป จึงประสานกันได้ จากนั้นสั่ง dream ใน console บน 5 session ย้อนหลัง 7 วัน dreaming ใช้ sub-agent วิเคราะห์ transcript คู่ขนาน และเสนอ diff เช่น พบ alert ที่เกิด 60 วินาทีหลัง CPU spike จึงบันทึกสมมติฐานเรื่อง retry behavior

ลำดับขั้นที่ทำในคลิป

  1. เดโม SRE: ระบบรับ alert/page แล้วสร้าง agent มา triage และแก้
  2. agent อ่าน memory store org-wide แบบ read-only (SLO policy, runbook, on-call mapping) และมี memory store read-write เฉพาะงาน
  3. agent หนึ่งหา root cause เปิด fix แล้วจดใน memory ว่า fix กำลังมา session ถัดไปที่เจอเหตุคล้ายกันอ่านแล้วรู้ทันที
  4. เปิดดู version history และ attribution ของการเขียน ซึ่งมี precondition จาก optimistic concurrency
  5. ใน Cloud console เปิดหน้า memory stores ดูไฟล์ใน team SRE store แล้วไปแท็บ Dreams
  6. สร้าง dream: เลือก store และ batch ของ session 7 วันล่าสุด (ราว 5 session) แล้วกด start
  7. ดู dream session (สร้างบน Managed Agents เอง ใช้ sub-agent วิเคราะห์ transcript คู่ขนาน) มี output memory store ที่กำลังคอมไพล์
  8. ดู diff ของ memory ที่ได้ เช่น บันทึก pattern alert หลัง CPU spike และจัด triage log ใหม่ให้เป็นภาพรวม

ตัวเลข / ข้อเท็จจริงที่ผู้พูดบอก

ตามที่ผู้พูดอ้างในคลิป ไม่ได้ยืนยันกับแหล่งอื่น

  • Rakuten: first-pass error ใน agent ที่ deploy จริงลด 97% (ตามที่ผู้พูดบอก)
  • Harvey: completion rate ใน legal benchmark เพิ่ม 6 เท่าเมื่อใช้ dreaming (ตามที่ผู้พูดบอก)
  • METR study ปี 2025 ที่ผู้พูดอ้าง: ความยาวงานที่ agent ทำได้เพิ่มเป็นสองเท่าทุก 7 เดือน
  • Opus 4.7 ถูกอธิบายว่า state of the art ด้าน file-system-based memory และเปิดตัว 'เดือนที่แล้ว'
  • เดโม dreaming: ใช้ 5 session จาก 7 วันล่าสุด พบ alert ที่ตามหลัง CPU spike 60 วินาที

สิ่งที่นำไปทำต่อ

  • ถ้าจะให้ agent เรียนรู้ ออกแบบ memory เป็นไฟล์ที่ Claude อ่านเขียนด้วยเครื่องมือที่เก่งอยู่แล้ว ไม่ต้องสร้างโครงซับซ้อน
  • แยก memory เป็นชั้น: ระดับองค์กรแบบ read-only กับระดับงานแบบ read-write เพื่อคุมสิทธิ์และคุณภาพ
  • เปิด version history และ attribution ไว้ เพื่อ audit และ diff ว่า memory เปลี่ยนไปยังไง
  • ถ้าหลาย agent เขียน memory ซ้ำซ้อน ให้พิจารณารัน dreaming เป็นรอบ (รายคืนหรือเมื่อจบ session) เพื่อ curate
  • ลองใช้ dreaming ใน research preview กับ memory store ของ managed agents ที่มีอยู่
