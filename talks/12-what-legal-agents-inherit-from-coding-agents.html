agent กฎหมายสืบทอดอะไรจาก coding agent: บทเรียนจาก Legora

What legal agents inherit from coding agents: Lessons from Legora

ผู้พูด: Jakob Emmerling (Engineer ที่ Legora (คำอธิบายคลิประบุ Staff Software Engineer; transcript สะกด Jacob))

เหมาะกับ: คนที่สร้าง agent ในโดเมนนอกเหนือจากงานโค้ด (กฎหมาย บัญชี การแพทย์ ฯลฯ) และอยากหยิบ pattern ของ coding agent ไปใช้

Jakob จาก Legora เสนอกรอบสามถังสำหรับสร้าง agent ในสายงานอื่นจากบทเรียนของ coding agent คือ นำมาใช้ตรงๆ (planning, sub-agents, human in the loop), แปลงให้เข้ากับโดเมน (แก้ docx ด้วย loop อ่าน-แก้-ตรวจ และ linting เอกสารกฎหมาย) และคิดใหม่เอง (citation, tabular review สำหรับ due diligence) ข้อสรุปคือให้โมเดลรู้สึกเหมือนอยู่ใน coding agent harness แล้วทำงานกฎหมาย

Legora's engineer shows a three-bucket framework for vertical agents: reuse coding-agent patterns, translate similar ones (docx editing loop, legal linting), and invent domain-specific pieces (citations, tabular review).

ประเด็นสำคัญ

  1. Legora สร้าง workspace AI ให้ทนายความ ผู้พูดบอกว่ามีลูกค้ากว่าพันราย รวมสำนักงานกฎหมายขนาดใหญ่ ก่อตั้งที่ Stockholm ราวหกเดือนก่อนพวกเขาตระหนักว่าโดเมนนอก coding ตามหลังอยู่ จึงเริ่มเรียนรู้จาก coding agent
  2. งานกฎหมายกับงานโค้ดคล้ายกันหลายด้าน ได้แก่ พึ่งงานเดิมมาก ทำกับเอกสารข้อความ มีข้อกำหนดเข้มในองค์กร และมีวัฒนธรรมรีวิว (partner รีวิวร่างของ associate เหมือน review PR) ผู้พูดบอกว่า knowledge work อื่นก็เทียบแบบนี้ได้
  3. สามถัง: (1) ใช้ซ้ำตรงๆ เช่น to-dos, planning, sub-agents, sandbox, human in the loop ซึ่งได้ฟรีเมื่อใช้ Anthropic agent SDK หรือ managed agents (2) แปลงให้เข้ากับโดเมน (3) สร้างใหม่ เช่น citation ที่อ้างอิงทุกคำตอบ และการทำงานกับเอกสารจำนวนมาก
  4. ตัวอย่างใช้ซ้ำ: planning mode ให้ทนายวางแผนและสำรวจบริบทก่อนให้ agent ลงมือ และการขออนุมัติ tool call ที่อันตราย (ไม่อยากให้ลบเอกสารลูกค้าเอง) ใช้ UX ที่ coding agent พิสูจน์แล้วโดยไม่ต้องคิดใหม่
  5. แปลงการแก้ docx: ระบบเดิมส่งเจตนาแก้ไปให้โมเดล reasoning อีกตัวแล้วแตกเป็นหลายคำสั่งย่อย ซึ่งมีปัญหา hand-off เมื่อ agent มี tool มากขึ้น ระบบใหม่ใช้ loop แบบ coding agent คือ read, edit, verify บน intermediate representation แบบข้อความเรียบของ docx
  6. POC แรกให้ agent แปลเอกสาร 10 หน้าจากอังกฤษเป็นสวีเดนทีละย่อหน้า ซึ่งงานนี้เคยทำให้ครบยากมาก agent วนอ่านเจอย่อหน้าที่ตกหล่นแล้วกลับไปแก้ ราว 10 นาทีก็แปลครบ และผู้พูดบอกว่ารันบน Haiku ด้วยซ้ำ
  7. ผู้พูดมอง mental model ว่าให้โมเดลรู้สึกเหมือนอยู่ใน coding agent harness แต่ทำงานกฎหมาย จะได้ประโยชน์จาก RL และ fine-tuning ที่ทำกับ harness แบบโค้ด และมี linting สำหรับเอกสารกฎหมาย (เช่นตรวจว่าการอ้างอิงข้ามข้อยังถูกต้องหลังลบย่อหน้า) พร้อมเพิ่มการ lint ด้วย LLM ได้
  8. สิ่งที่ต้องคิดใหม่คือ due diligence: Tabular Review เป็นตารางที่แถวคือเอกสารและคอลัมน์คือข้อมูลที่ให้ LLM สกัด agent ใช้เครื่องมือนี้เหมือนคนได้ และทนายตรวจคำตอบโดยดูเหตุผล citation และ mark verified เดโมแสดงทั้งการแก้สัญญาจ้างหลายฉบับพร้อม redline และจัดหมวดเอกสาร ~100 ไฟล์

ตัวเลข / ข้อเท็จจริงที่ผู้พูดบอก

ตามที่ผู้พูดอ้างในคลิป ไม่ได้ยืนยันกับแหล่งอื่น

  • Legora มีลูกค้ากว่า 1,000 ราย ตามที่ผู้พูดบอก
  • มูลค่าบริษัทเกิน $5 billion และเติบโตจาก 1 ไปถึง 100 million ARR แบบ 'record sprint' ตามที่ผู้พูดอ้าง
  • POC แปลเอกสาร 10 หน้า อังกฤษเป็นสวีเดนทีละย่อหน้า ใช้เวลาราว 10 นาที ด้วยโมเดล Haiku
  • เดโม due diligence ใช้เอกสารราว 100 ไฟล์ และเดโมแก้สัญญาจ้างเพิ่มวันหยุดคริสต์มาสหนึ่งสัปดาห์ให้ทุกคน
  • ตัวอย่างเทมเพลต 50 หน้าที่ต้องเติมหลายจุด ใช้อธิบายปัญหา exhaustiveness ของระบบเดิม

ประโยคเด่น (ต้นฉบับ)

“my mental model is kind of that you want to have the model almost feel like it's inside a coding agent harness, and it just does a legal task.”

mental model คือให้โมเดลรู้สึกเหมือนอยู่ใน coding agent harness แต่ทำงานกฎหมาย

“It's basically ESLint, but for legal documents.”

พูดง่ายๆ คือ ESLint สำหรับเอกสารกฎหมาย

“Whenever they ship something new, you steal the thing and benefit from it.”

พอ coding agent ปล่อยของใหม่ ก็หยิบมาใช้ได้เลย

สิ่งที่นำไปทำต่อ

  • จัดฟีเจอร์ของ agent ตัวเองเป็นสามถัง: ใช้ซ้ำ (planning, sub-agents, approval), แปลง, และสร้างใหม่ ก่อนเริ่มออกแบบ
  • ถ้าต้องแก้เอกสารที่ไม่ใช่ข้อความเรียบ ลองแปลงเป็น intermediate representation แบบข้อความแล้วใช้ loop read, edit, verify แทนการส่งต่อระหว่างโมเดลหลายตัว
  • เพิ่มตัวตรวจแบบ static (เช่นการอ้างอิงข้ามข้อ) เป็น feedback loop ให้ agent ในโดเมนของตัวเอง
  • เมื่อมีเอกสารจำนวนมาก ให้เครื่องมือแบบตาราง (แถวคือเอกสาร คอลัมน์คือข้อมูลที่สกัด) พร้อม citation เพื่อให้คนตรวจสอบได้
  • ติดตามฟีเจอร์ใหม่ของ coding agent แล้วดูว่าอะไรหยิบมาใช้หรือแปลงได้

ข้อควรระวังในสรุปนี้

  • transcript ถอดด้วย Whisper large-v3 ในเครื่อง ไม่ใช่ข้อความต้นฉบับของผู้พูด ชื่อเฉพาะอาจเพี้ยน (Cloud Code = Claude Code, 'Ligora' ในบางจุดคือ Legora, 'your diligence' = due diligence, 'tracing documents' อาจเป็นเอกสารยาวอื่น)
  • ชื่อผู้พูดสะกด Jacob ใน transcript แต่คำอธิบายคลิปใช้ Jakob จึงใช้ตามคำอธิบายคลิป และตำแหน่ง Staff Software Engineer มาจากคำอธิบายคลิป ไม่ใช่คำแนะนำตัวในเสียง
  • ตัวเลขบริษัท (ลูกค้ากว่า 1,000 มูลค่ากว่า $5 billion ARR 1 ถึง 100 million) เป็นข้ออ้างของผู้พูด ไม่ได้ตรวจสอบกับแหล่งอื่น และยอดเงินอาจฟังคลาดเคลื่อน
  • ช่วงท้ายเดโมมีประโยค 'It figured out the key points' ซ้ำหลายครั้งจาก ASR จึงไม่สรุปรายละเอียดตรงนั้น
  • เคส Haiku เป็นข้ออ้างจากประสบการณ์ POC ครั้งเดียว ไม่ใช่ผลการประเมินเชิงระบบ
