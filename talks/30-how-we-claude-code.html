ทำงานกับ Claude Code แบบทีม Anthropic: ให้ Claude สัมภาษณ์ เขียน spec เป็น HTML และฝัง verification ไว้ในตัวงาน

How we Claude Code

ผู้พูด: Arno (Applied AI team, architect (Anthropic))

เหมาะกับ: คนใช้ Claude Code อยู่แล้วและอยากรีดประสิทธิภาพให้งานที่ agent รันนานๆ ไม่เสียโทเค็นไปกับทิศทางผิด ควรรู้ React กับ Playwright เบื้องต้น

Arno จาก Applied AI team พาทำสามเฟส ให้ Claude สัมภาษณ์ขอ requirement ด้วย ask user question tool, สร้าง design หลายทางเป็นไฟล์ HTML ให้เทียบและให้ feedback แทน markdown ยาว และฝัง verification ให้ agent อ่านได้ผ่าน state ใน DOM ข้อสรุปคือยิ่ง agent รันนาน ยิ่งต้องย้าย verification ของมนุษย์ขึ้นมาไว้ต้นทาง

Anthropic's Arno shows three phases: let Claude interview you for specs, review design directions as HTML instead of markdown, and make verification agent-native by publishing state to the DOM.

ประเด็นสำคัญ

  1. โมเดลเก่งขึ้น agent รันนานขึ้น จึงต้องเปลี่ยนนิสัยการทำงาน ผู้พูดอ้าง bitter lesson ของ Richard Sutton ว่าอย่าไปบีบโมเดลมากเกินไป และให้ยอมรับว่า Claude น่าจะดึง requirement ออกจากคุณได้ดีกว่าที่คุณเขียนสเปกเอง
  2. prompt ที่ไม่ดีคือ 'make it better' หรือ 'make no mistakes' prompt ที่ดีให้ขอบเขตหัวข้อ ไม่ระบุผลลัพธ์ตายตัว แล้วสั่งให้ Claude ใช้ ask user question tool สัมภาษณ์ทีละข้อ ตัวอย่างคือแอปแบ่งบิลกับเพื่อน
  3. ผู้พูดแนะนำ auto mode (สลับด้วย shift tab) ตั้ง effort ที่ xhigh (หรือ max) ผ่าน /effort และลอง fast mode (/fast) สำหรับวนสเปกเร็ว ซึ่งแพงกว่าแต่ iterate ไว
  4. ไฟล์ markdown ยาวเกินราว 200 บรรทัดแทบไม่มีใครอ่าน HTML แน่นกว่าและมีปฏิสัมพันธ์ได้ ผู้พูดให้ Claude (Opus 4.7) สร้างสี่ทิศทางดีไซน์เป็น HTML (เช่น brutalist กับ Tokyo fintech) ให้คลิกเทียบแล้ว feedback ได้ตรงกว่า และอ้างบล็อกของ Tariq เรื่อง 'The Unreasonable Effectiveness of HTML files'
  5. การส่ง screenshot ให้ Claude ช่วยบอกสิ่งที่พูดยาก เช่น layout เพี้ยนเล็กน้อย ผู้พูดว่า Opus 4.7 มี vision model ดีขึ้นมาก และไม่แนะนำ Sonnet สำหรับงานนี้
  6. เฟสสามคือ verification ที่ agent-native บนแอป to-do ด้วย React: component เผยแพร่ state ลง DOM (data-verify attribute) มี schema, fixture, known states และ invariants ที่ต้องเป็นจริงเสมอ ตรวจด้วย probe และใช้ Storybook fixtures, testing library, Playwright MCP
  7. verification มีสามพื้นผิว dashboard ที่คนอ่านได้, agent ขับผ่านเบราว์เซอร์ และ headless ใน CI ด้วยคำสั่ง bun verify เดโมจงใจฝังความผิดพลาด (3 + 4 ไม่เท่า 10) และลบ stats ออกจาก DOM เพื่อให้เห็นว่าพังที่ contract ไม่ใช่ที่แอป แล้วให้ Claude (Opus 4.7 ผ่าน Playwright MCP) วินิจฉัยให้
  8. ผู้พูดบอกว่าทีม Claude Code บันทึกวิดีโอการ verify ของ frontend change เกือบทั้งหมด เก็บบน S3 หรือแชร์ให้เพื่อนร่วมทีม และกล่าวว่า HTML spec ไม่ได้เปลืองโทเค็นกว่าในระยะยาวเพราะต้องวนแก้น้อยลง

ลำดับขั้นที่ทำในคลิป

  1. Phase 1: เปิด Claude Code ตั้ง auto mode (shift tab), /effort เป็น xhigh, ลอง /fast แล้ววาง prompt ให้ Claude สัมภาษณ์ requirement ของแอปแบ่งบิลด้วย ask user question tool ตอบทีละข้อจนได้ spec
  2. Phase 2: สั่งให้ Claude สร้างสี่ทิศทางดีไซน์เป็น HTML แยกไฟล์ให้เทียบ เปิดคลิกดู แล้วถ่าย screenshot ส่ง feedback กลับ
  3. Phase 3: โหลดแอป to-do (React) ดู element ที่ publish state ลง DOM (data-verify unit, total, done, active) พร้อม schema, fixtures, invariants
  4. รัน verification dashboard ให้คนดู กดรันทั้งหมด พบเคสที่ฝังความผิด 3 + 4 != 10
  5. ให้ agent ขับผ่านเบราว์เซอร์ด้วย Playwright MCP อ่าน manifest ของ verification ที่อยู่ใน DOM แล้วรันเอง และบันทึกเป็นคลิปเป็นหลักฐาน
  6. ทดลองทำลาย contract (ลบ total stats ออกจาก DOM) เพื่อดูว่าเทสต์ล้มเพราะ contract ไม่ใช่แอป
  7. ให้ Claude (Opus 4.7) วินิจฉัยสาเหตุที่ verify ล้ม และรัน headless ด้วย bun verify แบบ CI
