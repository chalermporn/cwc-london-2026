สามบริษัทยุโรปปรับเป็น AI-native บนโค้ดเก่า (monday.com, Doctolib, Delivery Hero)

Building AI-native at enterprise scale: monday.com, Doctolib, and Delivery Hero

ผู้พูด: Rebecca (Anthropic Go-To-Market team (ผู้ดำเนินรายการ)); Ruslan (ชื่อเพี้ยนใน ASR: ถูกเรียกต่างกันหลายแบบ) (engineering leader ที่ monday.com); Alex (ตัวแทน Doctolib (ที่ transcript เขียนว่า Dr. Lib); ตำแหน่งไม่ได้ยิน); Ulrich Schäfer (VP Tech Foundations ที่ Delivery Hero)

เหมาะกับ: ผู้นำวิศวกรรมหรือทีม platform ในองค์กรขนาดใหญ่ที่มี codebase เก่าและกำลังวางแผนนำ Claude ไปใช้ทั้งภายในและในผลิตภัณฑ์

แพเนลผู้นำเทคโนโลยีจากสามบริษัทที่ก่อตั้งก่อนยุค LLM เล่าว่าปรับเป็น AI-native บน codebase เก่ายังไง Delivery Hero สร้าง agent HeroGen ที่ส่ง PR เข้า production เฉลี่ย 173 รายการต่อวัน, Doctolib ทำ skills marketplace ให้ทั้งองค์กร, monday.com ใส่ Claude ในตัวผลิตภัณฑ์ (monday Vibe) บทสรุปร่วมคือ ลองใช้เลย อย่ารอสภาพที่สมบูรณ์ และเมื่อโมเดลเปลี่ยนต้องวัดแบบ end-to-end

Panel of Delivery Hero, Doctolib and monday.com leaders on becoming AI-native on old codebases: an autonomous PR agent, an org-wide skills marketplace, and in-product vibe coding, with advice to start now and evaluate model changes end-to-end.

ประเด็นสำคัญ

  1. ทั้งสามบริษัทก่อตั้งช่วง 2011-2013 ก่อนยุค LLM และไม่มีใครเริ่มจาก greenfield monday.com อายุราว 14 ปี เป็น monolith ที่กำลังแยกออก, Doctolib ครึ่งหนึ่งเป็น monolith อายุกว่าทศวรรษ อีกครึ่งเป็น distributed services ใหม่, Delivery Hero ให้บริการกว่า 60 ตลาด
  2. Delivery Hero (Ulrich): สร้าง HeroGen ระบบ autonomous software delivery รับ Jira ticket หรือ GitHub issue แล้วทำจนได้ PR ที่ merge ได้ พัฒนาช่วงครึ่งหลังของปีก่อน เปิดตัว Q1 ผู้พูดบอกว่าเฉลี่ย 173 PR ที่ merge เข้า production ต่อวันในช่วง 10 วันล่าสุด และราว 7,000 PR ตั้งแต่เปิดตัวเดือนกุมภาพันธ์
  3. Doctolib (Alex): ผู้พูดบอกว่าพนักงานใช้ Claude ใกล้ 100% รวมถึงสายที่ไม่ใช่ engineer หลักคิดคือให้ platform team เป็นผู้เปิดทางและทำให้แนวปฏิบัติที่ดีขยายต่อ จึงสร้าง skills marketplace ดู skill ที่ถูกใช้มากและมาแรงได้ มี environment ที่ต่อ tool ให้พร้อมและแพ็ก skill เข้าไปตั้งแต่ onboarding รวมทั้งช่อง Build with AI ที่คึกคักที่สุดของบริษัท
  4. monday.com (Ruslan): ใช้ Claude ทั้งภายในและในผลิตภัณฑ์ monday Vibe แปลง prompt เป็น PRD แล้วสร้างแอปในนาที ทำ POC ได้ในไม่กี่วันเพราะลงทุน open platform ให้นักพัฒนาภายนอกไว้ก่อน ทำให้ Vibe ใช้ API, SDK และ deployment ชุดเดียวกับนักพัฒนาภายนอก ส่วนที่ยากต่อคือการทำให้ทุกฟีเจอร์เปิดผ่าน API
  5. เมื่อโมเดลเปลี่ยน Delivery Hero (Ulrich) บอกว่า Opus รุ่นเมื่อพฤศจิกายนปีก่อนคือจุดที่ HeroGen ใช้งานได้จริง และยังอยู่กับ Opus 4.5 เพราะยังไม่มี A/B testing กับ volume พอจะตัดสินย้ายโมเดล ส่วน Doctolib (Alex) มีทีม eval เข้มงวดสำหรับผลิตภัณฑ์ AI แต่ฝั่ง development process ยังเป็นความรู้สึกอยู่
  6. monday.com (Ruslan) เล่าว่าตอนย้ายจาก Opus 4.5 เป็น 4.6 system prompt ที่จูนไว้ย้ายมาไม่ได้ ต้องคิดและจูนใหม่ โดยทำงานใกล้ชิดกับ solution engineers ของ Anthropic ระบบของ Vibe เป็น multi-model (มี orchestrator กับ workflow ที่มี action แบบ deterministic) จึงต้องวัด end-to-end แล้วตามด้วย A/B test
  7. สถาปัตยกรรมของ HeroGen ต่อเข้า Jira, GitHub Issues (เร็วๆ นี้ GitLab) แทนที่จะสร้างหน้าแชตใหม่ ต่อ CI เพื่อป้อน failure กลับให้ agent แก้ และต่อกับทีม security ให้ช่องโหว่ระดับโค้ดถูก assign ให้ agent ผู้พูดบอกว่า success rate (สัดส่วน PR ที่ merge ต่อที่ถูกปฏิเสธ) ขึ้นถึง 85% เพราะ council of agents คือหลายโมเดลรีวิวโค้ดเดียวกันเพื่อลดจุดบอด โดยต้นทุนไม่ได้เพิ่มมากอย่างที่คาด
  8. บทเรียนด้านสถาปัตยกรรมจาก Doctolib (Alex) คือ codebase เล็กที่มีมาตรฐานและเอกสารชัดทำให้โมเดลทำงานดีกว่า ใน monolith ต้องบอกบริบทเพิ่มว่าแบบไหนคือวิธีใหม่ อีกข้อคือ bottleneck ย้ายที่ ต้องคิดกระบวนการใหม่ ไม่ใช่แค่โค้ด ส่วน monday.com (Ruslan) จะเน้น API-first ให้เร็วกว่านี้ และออกแบบ identity กับ permission ให้ agent เป็น first-class user
  9. ช่วง lightning round ผู้ร่วมแพเนลเอนไปทาง specialist agents หลายตัวที่มี generalist ประสานงาน วิศวกรระดับสูงกลับมาลงมือสร้างโค้ดและสร้าง context layer (ที่เรียกว่า AI brains) และคำแนะนำปิดท้ายคือเริ่มใช้เลย โดย Delivery Hero ตั้ง mandate ให้ทุกทีมทำฟีเจอร์แบบ end-to-end ด้วย AI ในไตรมาสนี้

ตัวเลข / ข้อเท็จจริงที่ผู้พูดบอก

ตามที่ผู้พูดอ้างในคลิป ไม่ได้ยืนยันกับแหล่งอื่น

  • Delivery Hero / HeroGen (Ulrich): เฉลี่ย 173 PR ที่ merge เข้า production ต่อวันในช่วง 10 วันล่าสุด และราว 7,000 PR ตั้งแต่เปิดตัวเดือนกุมภาพันธ์ (คำอธิบายคลิปเขียนว่า merge 100+ PR ต่อวัน)
  • Delivery Hero: success rate ของ HeroGen = PR ที่ถูก merge ต่อ PR ที่วิศวกรปฏิเสธโดยตรง ผู้พูดบอกว่าขึ้นถึง 85% จาก council of agents
  • Delivery Hero: ยังใช้ Opus 4.5 ตั้งแต่ Opus รุ่นเดือนพฤศจิกายนปีก่อนที่ทำให้ระบบใช้งานได้จริง
  • monday.com (Ruslan): บริษัทอายุราว 14 ปี; ย้ายจาก Opus 4.5 เป็น 4.6 แล้วต้องจูน system prompt ใหม่
  • Doctolib (Alex): ผู้พูดบอกว่าการใช้ Claude อยู่ใกล้ 100%; codebase ครึ่งเป็น monolith อายุกว่าทศวรรษ อีกครึ่งเป็น distributed ที่สร้างในไม่กี่ปีนี้; PR ราวครึ่งหนึ่งยังเข้า monolith
  • Delivery Hero: ให้บริการกว่า 60 ตลาด

ประโยคเด่น (ต้นฉบับ)

“you need to build for the next model, not for the current one”

ต้องสร้างเพื่อโมเดลรุ่นถัดไป ไม่ใช่รุ่นปัจจุบัน

“It's literally treating it as a completely different thing.”

ต้องปฏิบัติต่อโมเดลใหม่ราวกับเป็นของคนละอย่างเลย

“stop waiting for perfect conditions, perfect use cases, also enough AI-ready work”

เลิกรอสภาพที่สมบูรณ์ use case ที่สมบูรณ์ หรืองานที่พร้อมสำหรับ AI

สิ่งที่นำไปทำต่อ

  • ต่อ agent เข้ากับจุดที่ทีมทำงานอยู่แล้ว เช่น Jira, GitHub, CI แทนการสร้างหน้าแชตใหม่ เพื่อให้คนยอมใช้
  • ลองให้หลายโมเดลรีวิวโค้ดเดียวกัน (council of agents) เพื่อลดจุดบอดของโมเดลตัวเดียว
  • ตั้ง platform team ให้ทำหน้าที่เก็บแนวปฏิบัติที่วิศวกรคิดค้นเอง แล้วแพ็กเป็น skills marketplace กับ environment ที่พร้อมใช้ตั้งแต่ onboarding
  • ก่อนเปลี่ยนรุ่นโมเดล เตรียม A/B testing กับ eval แบบ end-to-end และเผื่อเวลาจูน prompt ใหม่ อย่าสมมติว่าใช้แทนกันได้
  • ถ้าจะเปิดระบบให้ agent เรียกใช้ ลงทุน API ที่สะอาดและ identity/permission ที่รองรับ agent ให้เร็ว
  • เริ่มจากงานซ้ำๆ ที่เป็นภาระ ปล่อยให้ Claude ทำเต็มที่ แทนการรอ refactor ใหญ่เสร็จก่อน

ข้อควรระวังในสรุปนี้

  • transcript มาจาก Whisper large-v3 ที่ถอดเอง ไม่แยกผู้พูด การระบุว่าใครพูดอะไรอนุมานจากการแนะนำตัวและที่ผู้ดำเนินรายการเรียกชื่อ
  • ชื่อผู้ร่วมแพเนลจาก monday.com ถูกเรียกต่างกันใน transcript (Ruslan / Rosalind / Roslyn / Rodrigue) น่าจะเป็นคนเดียวกันที่แนะนำตัวว่า Ruslan แต่ไม่แน่ใจ; ชื่อ Alex มาจากที่ผู้ดำเนินรายการเรียก และ ASR สะกดบริษัทเป็น Dr. Lib ซึ่งตรงกับชื่อใน title คลิปคือ Doctolib
  • ส่วน lightning round ผู้ตอบแต่ละข้อไม่ชัด เพราะไม่แยกผู้พูด (เช่น คำตอบเรื่อง specialist กับเรื่องวิศวกรระดับ principal กลับมาเขียนโค้ด และ metric ที่ดูทุกเช้า) จึงสรุปเป็นภาพรวม ยกเว้นข้อที่บริบทชัด
  • transcript ช่วงคำตอบเรื่อง best engineers มีประโยคซ้ำและขาดตอน (ASR เสียหาย) เนื้อหาตรงนั้นอ่านต่อเนื่องไม่ได้ทั้งหมด
  • ตัวเลขและ success rate 85% เป็นข้ออ้างของผู้พูด ไม่มีหลักฐานอิสระ; ตัวเลข 173 ต่อวันเป็นค่าเฉลี่ย 10 วันล่าสุด ขณะที่คำอธิบายคลิปเขียน 100+ ต่อวัน
  • ชื่อโมเดลที่ฟังได้ (Opus 4.5, 4.6) มาจาก ASR ยังไม่ได้ยืนยันกับแหล่งอื่น; monday.com ใช้คำว่า post-model ซึ่งน่าจะหมายถึงโมเดลระดับ Opus แต่ไม่แน่ใจ
