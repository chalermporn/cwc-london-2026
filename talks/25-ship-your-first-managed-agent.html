เวิร์กชอปสร้าง incident-investigator agent ตัวแรกบน Claude Managed Agents

Ship your first Managed Agent

ผู้พูด: Isabella He (Member of technical staff, Applied AI team, Anthropic (ชื่อจาก auto-caption))

เหมาะกับ: นักพัฒนาที่เคยเรียก Claude API มาบ้าง อยากเห็นว่า Managed Agents ประกอบกันยังไงตั้งแต่ศูนย์ (ใช้ Python กับ Streamlit)

เวิร์กชอปพาสร้าง SRE agent ที่สืบสวน incident ได้จริงบน Claude Managed Agents โดยประกอบจาก primitive 4 ตัว คือ agent, environment, session และ event stream พร้อม local tools ผู้พูดเน้นว่า agent loop รันฝั่ง server ส่วน tool รันที่ไหนก็ได้ เลยข้ามงาน hosting กับ durability ไปได้ แล้วจบด้วยแผนที่ฟีเจอร์ถัดไป เช่น subagents, memory, outcomes, vaults

A hands-on workshop building an SRE incident-investigator agent on Claude Managed Agents from agent, environment, session and event streaming primitives, plus local tools, with the agent loop running server-side.

ประเด็นสำคัญ

  1. ผู้พูดเล่าลำดับวิวัฒนาการ Messages API (ได้แค่ tokens in/out ต้องทำ context management, agent loop, compaction เอง) มา Agent SDK (ยังต้อง host และ scale เอง) แล้วมาเป็น Claude Managed Agents ที่ Anthropic ดูแล harness, sandboxing, observability, tool runtime ให้
  2. เหตุผลที่ harness ต้องวิวัฒนาการตาม agent: ตอนใช้ Sonnet 4.5 เจอพฤติกรรม context anxiety (Claude รีบจบงานทั้งที่ context ยังเหลือ) ต้องใส่ mitigation ใน harness พอ Opus 4.5 ออกมาพฤติกรรมนี้หายไป งานที่ทำไว้เลยล้าสมัย
  3. ทรัพยากรหลัก 3 อย่าง: agent (persona + ความสามารถ: model, system prompt, MCP, skills) เปรียบเป็นสมอง, environment (container ที่ลงมือทำงาน) เปรียบเป็นมือ, session ผูกสองอย่างเข้าด้วยกันแล้ว stream event กลับมา
  4. การแยกมือออกจากสมอง (decouple agent loop จาก tool execution) ช่วยเรื่อง credentials กับ security และลด latency เพราะไม่ต้อง spin up container ทุก session ผู้พูดอ้างว่า TTFT ที่ P95 ลดลงเกิน 90%
  5. ภาคปฏิบัติทำใน agent.py ทีละขั้น: สร้าง agent (SRE agent, Opus 4.7, system prompt สั้นๆ, tools) แล้ว environment (cloud, networking แบบ unrestricted หรือจำกัดเป็น allow list) แนบไฟล์ log ผ่าน files API ผูกทุกอย่างเข้า session แล้ว stream event
  6. session ทำงานเป็นหน่วย event (user message, tool call, agent response) ไม่ใช่ request/response ทำให้ log ได้ stream ให้ผู้ใช้เห็นทีละส่วนได้ และ resume ได้ง่าย ถ้า container ล้มก็ spin ใหม่โดยไม่ต้องเริ่ม agent loop ใหม่
  7. agent บน server รู้จัก local tools (get metrics, get recent deploys, get diff) ผ่านโค้ดฝั่งเรา ผลลัพธ์ในเดโม agent สืบจนได้สาเหตุเป็น database pool exhaustion จาก commit ที่ refactor order summary builder พร้อมคำแนะนำ ผู้พูดบอกว่าย้าย tool ไปใช้ Datadog จริงได้ด้วย wire protocol เดิม
  8. state ของ session (idle, running, rescheduling, terminated) ช่วยให้ resume ได้และรับ webhook เพื่อปลุก session ตาม event ภายนอกได้ ข้อมูลอยู่บน cloud จึงไม่ต้องทำ database เอง และลบ session ได้ถ้าไม่อยากให้เก็บ
  9. ฟีเจอร์ต่อยอดที่ผู้พูดไล่ให้: skills, subagents (orchestrator + context window แยก), memory กับ dreaming, outcomes (กำหนด rubric ผลลัพธ์), vaults (เก็บ credentials เข้ารหัสแยกจากที่ agent เข้าถึง), webhooks, permission policies, MCP server controls และ console agent builder

ลำดับขั้นที่ทำในคลิป

  1. เตรียมเครื่อง: git clone repo เวิร์กชอป แล้ว cd เข้าโฟลเดอร์ ship your first managed agent, สร้าง virtual env (Python), ติดตั้ง requirements, ก๊อป env key ใส่ไฟล์ .env ด้วย Anthropic API key
  2. รันแอปด้วย streamlit run app.py แล้วเปิด URL ที่ได้
  3. เปิด agent.py (ฉบับว่าง) เทียบกับ agent complete แล้วก๊อปทีละส่วนจากฉบับเสร็จมาใส่
  4. ขั้น 1 agent: นิยาม SRE agent ด้วย model Claude Opus 4.7, system prompt สั้นๆ (บอกว่าเป็น SRE agent ที่ debug incident), และ tools เช่น metrics, recent deployments, get diff, fetch logs
  5. ขั้น 2 environment: กำหนด environment บน Anthropic cloud และ networking แบบ unrestricted (เปลี่ยนเป็น allow list จำกัด URL ได้)
  6. ขั้น 3 อัปโหลดไฟล์ metrics/logs เข้า agent ผ่าน files API เพื่อให้ agent รันโค้ดประมวลผลไฟล์
  7. ขั้น 4 session: ผูก agent ID, environment ID และ resources (ไฟล์ log ที่ mount)
  8. ขั้น 5 stream events: รับ event (user message, tool call, agent response) กลับมาแสดงผลทีละส่วน
  9. ขั้น 6 local tools: ต่อ handler ฝั่งเครื่องเราให้ get metrics, get recent deploys, get diff แล้วเพิ่มปุ่ม delete session
  10. ทดสอบ: new session แล้วสั่ง debug my incident ดู tool call ที่ stream เข้ามา จนได้ root cause และ recommended actions
  11. ลอง hard refresh เพื่อเห็นว่า session ยังอยู่บน cloud, ลบ session, และดูสถานะ idle กับ running แล้วถามต่อใน session เดิม (เช่น Who are you?)

ตัวเลข / ข้อเท็จจริงที่ผู้พูดบอก

ตามที่ผู้พูดอ้างในคลิป ไม่ได้ยืนยันกับแหล่งอื่น

  • ผู้พูดอ้างว่าทีมต่างๆ สร้างถึง production ได้เร็วขึ้น 10 ถึง 15 เท่าด้วย Claude Managed Agents
  • ผู้พูดอ้างว่า time to first token ที่ P95 ลดลงเกิน 90% หลังแยก agent loop ออกจาก tool execution
  • โมเดลในเดโม: Claude Opus 4.7 (ใช้กับ SRE agent)
  • ตัวอย่าง incident ในเดโม: P99 latency สูงกว่า baseline ประมาณ 10 เท่า
  • ตัวอย่าง context anxiety: เกิดกับ Sonnet 4.5 และหายไปใน Opus 4.5
  • เวิร์กชอปเป็นคลิป 37:09 และบอกว่า agent ทั้งหมดทำได้ใน six functions ตามคำอธิบายคลิป

สิ่งที่นำไปทำต่อ

  • ถ้าจะทำ agent ใหม่ ลองแยกคิดเป็น agent (สมอง) กับ environment (มือ) กับ session ก่อนลงมือ จะวางตำแหน่ง tool ได้ชัดขึ้น
  • ให้ข้อมูลกับ agent ให้มากที่สุดผ่านไฟล์ (files API) ผู้พูดมองว่า context engineering คือที่ที่นักพัฒนาควรใช้เวลา
  • ออกแบบ UI ให้ stream event ตั้งแต่ต้น ทั้งเพื่อประสบการณ์ผู้ใช้และเพื่อ observability
  • เริ่มด้วย local tool ที่อ่าน JSON ก่อน แล้วค่อยสลับเป็นระบบจริง เช่น Datadog ทีหลัง
  • ถ้าทำ SRE agent จริง ลองเพิ่ม skill ที่ถือ runbook และ postmortem เก่า เหมือนที่คนใช้ตอน debug
