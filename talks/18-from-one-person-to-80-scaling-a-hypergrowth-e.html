From one person to 80: Scaling a hypergrowth engineering org with Claude Code

ผู้พูด: Yoav (lead product ที่ Base44); Gabriel (lead ฝั่ง AI (app builder agent) ที่ Base44)

เหมาะกับ: ทีมสตาร์ทอัพหรือ product engineering ที่กำลังโตเร็วและอยากรู้ว่าจะใช้ Claude Code จัดการ onboarding รีวิว ทดลอง และ QA โดยไม่สร้างกระบวนการหนัก

ทีม Base44 เล่าว่าเมื่อทีมโตจากวิศวกรคนเดียวเป็นราว 80 คน (หลัง Wix เข้าซื้อและควบรวมทีมอื่น) ใช้ Claude Code แก้คอขวดทีละช่วงด้วยวิธีที่เรียบง่ายตั้งใจ เช่น prompt เดียวช่วย onboard, ให้ Claude สรุป comment จาก PR เก่าเป็นกฎรีวิว, ใช้ frustration ของผู้ใช้เป็นสัญญาณ A/B test, แล้วช่วงหลังขยับเป็น bot ตัดสิน experiment, eval ที่มี user simulator และ QA agent บนเบราว์เซอร์

Base44 leaders show how they used Claude Code to remove onboarding, code review, experimentation, eval and QA bottlenecks while growing from one engineer to ~80, keeping each solution deliberately simple.

ประเด็นสำคัญ

  1. Base44 เป็นแพลตฟอร์ม vibe coding เริ่มโดย solo founder ปลายปี 2024 ผู้พูดบอกว่ามีกำไรภายในเมษายน 2025 แล้ว Wix เข้าซื้อ ทีมจึงขยายอย่างรวดเร็วจากสองคนเป็นราว 15 วิศวกร และเจอ 4 ปัญหา คือ onboarding, code review, การทดสอบกับผู้ใช้ และ product surface ที่กว้าง
  2. หลักที่ย้ำทั้งงานคือ keep everything simple onboarding ไม่ทำเอกสารที่ต้องอัปเดต แต่ให้วิศวกรใหม่รัน 2 prompt คือให้ Claude ไล่ commit ทั้งหมดแล้วบอกว่าใครสนใจอะไร (ได้แผนที่องค์กร) และขอ mermaid chart ว่า component ที่จะแตะทำงานยังไง ผู้พูดเล่าว่าวิศวกรใหม่ทำ WhatsApp integration เสร็จตั้งแต่พฤหัสถึงเช้าวันอาทิตย์ จากที่คาดว่า 1-2 สัปดาห์
  3. Code review ไม่สเกลเพราะผู้ก่อตั้งดูแลทุก PR ทีมให้ Claude อ่าน comment จาก PR ที่สะสมใน repo แล้วสรุปสิ่งที่สำคัญที่สุดเป็น instruction สำหรับรีวิว รันซ้ำทุกไม่กี่วัน แทนการนั่งคิดกฎเอง
  4. การวัดคุณภาพ agent: ทีมเล็กเกินจะทำ eval suite เต็มรูป จึงใช้ข้อสังเกตว่าเมื่อทุกอย่างปกติผู้ใช้เงียบ ถ้าพังจะเสียงดัง ให้โมเดลเล็ก (ผู้พูดเรียกในที่นี้ว่า Haiku) จัดระดับ frustration ของแต่ละข้อความ แล้วปล่อยเวอร์ชันใหม่ให้ผู้ใช้เปอร์เซ็นต์น้อยๆ และดู frustration ใช้ได้ทั้งตอนเปลี่ยน infra, prompt หรือโมเดล
  5. ช่วงสอง ทีมโตจาก 40 เป็นราว 80 คนในคืนเดียวหลังรับคนภายนอก คนย้ายจาก Wix และควบรวมอีกผลิตภัณฑ์ (ในช่วงแนะนำ Yoav พูดว่า 50 ถึง 80) Gabriel เล่า 3 ปัญหา คือสเกลการทดลอง, eval และ QA
  6. Experimentation: สร้าง bot ที่คอมเมนต์บน PR ว่า ship ได้เลย graduate หรือต้อง A/B test นานเท่าไร ใช้ KPI อะไร และเปิด experiment บน PostHog (transcript เขียน post-hoc) ให้ ส่วนกฎ ทีมไม่ตั้งคณะกรรมการ แต่ให้ Claude กลั่นจาก 100 experiment ล่าสุดกับ PR ที่ตรงกัน ผ่าน PostHog MCP ได้ร่างแรกใน 2-3 ชั่วโมง แล้วทำ dashboard กลางด้วยผลิตภัณฑ์ตัวเอง ต่อ BigQuery, PostHog, GitHub
  7. Evals: ทีมไม่มีกำลังทำโครงการสามเดือน จึงสร้าง user simulator ที่เมื่อแอปบางส่วนใช้ไม่ได้ ไม่ถือว่า eval ล้ม แต่ส่งข้อความปฏิเสธกลับไปให้ agent แก้ต่อ แล้ววัด latency จำนวนรอบ ต้นทุน และ credits CI/CD จะเปิดแอป Base44 จริงทุกครั้งที่โค้ด AI เปลี่ยน และใช้ Stagehand จำลองการกระทำผู้ใช้ มี scenario ที่ทดสอบ compaction ด้วย
  8. QA: ห่อ flow หลักไว้เป็น skills ให้ Claude Code ใช้เบราว์เซอร์ (Playwright MCP) โดยไม่ต้องเรียนรู้แพลตฟอร์มใหม่ทุกครั้ง ทำ CLI ที่ซ่อน API/database เพื่อ setup สถานการณ์ทดสอบ แล้วรวมเป็น meta skill ว่าด้วย QA เมื่อเปิด PR agent จะวางแผนทดสอบ ทดสอบกับแอป Base44 และรายงานพร้อม screenshot ผู้พูดบอกว่าใช้ได้ราว 80% ของเวลา
  9. บทสรุป: เรียบง่ายและเลื่อนสิ่งที่ซับซ้อน (เช่น eval) ไปจนถึงจังหวะที่เหมาะ, เข้ารหัส taste ของทีมจากการกระทำที่ผ่านมา, ใช้ผลิตภัณฑ์ตัวเองถ้าทำได้ และ bottleneck จะย้ายที่เรื่อยๆ ตอนนี้กำลังทำ post-validation หลัง PR ถึง production

ตัวเลข / ข้อเท็จจริงที่ผู้พูดบอก

ตามที่ผู้พูดอ้างในคลิป ไม่ได้ยืนยันกับแหล่งอื่น

  • Base44 เริ่มปลายปี 2024 และมีกำไรภายในเมษายน 2025 ตามที่ผู้พูดเล่า
  • ขนาดทีม: จาก solo founder เป็นราว 15 วิศวกรหลัง Wix เข้าซื้อ แล้วจาก 40 เป็นราว 80 คนในคืนเดียว (ช่วงแนะนำพูดว่า 50 ถึง 80 ซึ่งขัดกับช่วงหลัง)
  • WhatsApp integration: คาดว่า 1-2 สัปดาห์ แต่วิศวกรใหม่ onboard วันพฤหัสแล้ว PR พร้อมเช้าวันอาทิตย์ มีคอมเมนต์รีวิวจาก PR model แค่ 2-3 ข้อ
  • กลั่นกฎ experiment จาก 100 experiment ล่าสุดใน PostHog ได้ร่างแรกภายในไม่กี่ชั่วโมง
  • ระยะเวลาทดสอบต่อฟีเจอร์: บางตัว 7 วัน บางตัวต้องเต็มเดือนเพราะกระทบ conversion และ premium rate ในระดับเปอร์เซ็นต์เล็กๆ
  • QA skill ครอบคลุมประมาณ 80% ของเวลา ที่เหลือ agent จะเขียนว่าทดสอบไม่ได้และชี้ความสามารถที่ขาด; skill ไม่จำเป็นต้องครอบคลุม 100% แค่ราว 80% ของ flow

ประโยคเด่น (ต้นฉบับ)

“you need to keep everything very very simple”

ต้องรักษาทุกอย่างให้เรียบง่ายมากๆ

“when things start to break, that's when users get really, really loud inside the chat”

พอของเริ่มพัง ผู้ใช้จะเสียงดังขึ้นมากในแชต

“the bottleneck will keep moving”

bottleneck จะย้ายที่ไปเรื่อยๆ

สิ่งที่นำไปทำต่อ

  • แทนเอกสาร onboarding ที่ต้องอัปเดต ลองให้คนใหม่รัน prompt ให้ Claude สรุป commit history และวาด mermaid ของ component ที่จะแตะ
  • ให้ Claude กลั่น comment รีวิวเก่าเป็นไฟล์ instruction แล้วรันซ้ำเป็นระยะ เพื่อขยายมาตรฐานของคนรีวิวหลัก
  • ถ้ายังไม่พร้อมทำ eval ใหญ่ ใช้ frustration ของผู้ใช้เป็น metric ในการ A/B test เวอร์ชัน agent
  • ห่อ flow ที่ทดสอบซ้ำบ่อยเป็น skills และทำ CLI สำหรับ setup ข้อมูลทดสอบ เพื่อให้ Claude Code ทำ QA ผ่านเบราว์เซอร์ได้
  • ให้ Claude กลั่นกฎการตัดสินใจ (เช่น เมื่อไรต้อง A/B test) จากประวัติการทำงานจริง แล้วค่อยปรับต่อ ไม่ต้องตั้งคณะกรรมการ

ข้อควรระวังในสรุปนี้

  • transcript มาจาก Whisper large-v3 ที่ถอดเอง ไม่แยกผู้พูด ชื่อเฉพาะอาจเพี้ยน: Yoav และ Gabriel ผู้พูดแนะนำตัวเองในคลิปจริง แต่ไม่มีนามสกุล
  • ASR เพี้ยนหลายจุด: post-hoc = น่าจะ PostHog, Naiku = น่าจะ Haiku, stage hand = Stagehand, ชื่อผู้ก่อตั้งที่ถูกเรียกว่า Maur/More น่าจะเป็นคนเดียวกันแต่สะกดไม่แน่ใจจึงไม่ระบุ
  • ตัวเลขขนาดทีมไม่สอดคล้องกัน: ช่วงแนะนำพูดว่าจาก 50 ถึง 80 แต่ช่วงเนื้อหาบอกว่า 40 เป็นราว 80 และช่วงแรก 15 วิศวกร ผู้พูดอาจพูดผิดหรือ ASR ฟังผิด
  • ช่วงเดโม eval ใน transcript มีประโยคซ้ำและเสียหาย (ฟังไม่ได้ว่าเดโมแสดงอะไร) จึงสรุปได้เฉพาะที่พูดไว้ ไม่รวมสิ่งที่อยู่บนหน้าจอ
  • ผลลัพธ์ทั้งหมด (เช่น QA ใช้ได้ 80%, PR ผ่านใน Thursday-Sunday) เป็นคำอ้างของผู้พูด ไม่มีตัวเลขเชิงสถิติรองรับในคลิป
