สอน agent ให้เรียนรู้จากทีม: เคส Buzz ของ Warp กับ feedback loop รายวัน

Teaching agents to learn from your team

ผู้พูด: Petra (Head of developer experience, Warp)

เหมาะกับ: คนที่สร้าง agent ประจำวันแล้วติดอยู่ที่ 80% (ใช้ได้เกือบแต่ไม่กล้าปล่อยเอง) โดยเฉพาะงานที่ต้องใช้ดุลพินิจ

Petra จาก Warp เล่าเคส Buzz agent ตอบ mention ในโซเชียลที่ต้องใช้ judgment และ taste ซึ่งเทสต์อัตโนมัติวัดไม่ได้ เธอแก้ด้วยสามอย่างที่ต้องมาด้วยกัน ได้แก่ เขียน skill เป็น principles แทน rules, สอนให้ agent เรียนรู้ว่าต้องแก้ instruction ตรงไหน และออกแบบ feedback loop รายวันผ่าน Slack emoji กับ pull request ข้อสรุปคือให้ลงแรงกับ feedback loop มากกว่าการขัด prompt แรกให้สมบูรณ์

Warp's Buzz agent handles judgment-heavy social replies by using principles instead of rules, a skill that teaches it to learn from feedback, and a daily Slack-to-PR loop; design the feedback loop rather than the perfect first prompt.

ประเด็นสำคัญ

  1. ผู้พูดถามผู้ฟังว่าใครเคยสร้าง agent ที่รันประจำแล้วยังใช้งานจริงและพอใจ มือลดลงมาก จึงตั้งโจทย์ว่า agent มักตายที่ช่อง 80% ที่ยังต้องคอยแก้ prompt จนแย่กว่าไม่มี agent
  2. Buzz เป็น agent ของ Warp ที่ดู social mentions แล้วตัดสินว่าจะ reply, like หรือ skip พร้อมร่างข้อความให้ ประกอบด้วยราว 15 skills แทบไม่มีโค้ด สร้างได้ในไม่กี่วัน และต่อกับ X API กับ Slack
  3. ทำไม loop แบบ Ralph loop ใช้ไม่ได้ตรงๆ: ต้องมี external check ที่ชัด (unit test, browser) งานที่ต้องใช้ judgment และ taste ไม่มีเทสต์ และ feedback จริงจากชุมชนช้าและซับซ้อน
  4. การลองครั้งแรกคือขัด prompt ผลออกมาเป็น checklist ของกฎ if X then Y ฟังเหมือนหุ่นยนต์และแตกเมื่อเจอสถานการณ์ใหม่ จึงสลับเป็น principles แบบที่อธิบายให้เพื่อนร่วมทีมใหม่ ผลคือ skill file สั้นลงราวหนึ่งในห้าแต่ output ดีขึ้น
  5. พอให้ agent เรียนจาก feedback มันกลับไปเพิ่มกฎเฉพาะเคส (เช่น อย่าพูดเรื่องราคาในบรรทัดแรก) จึงต้องสอน 'วิธีเรียน' ด้วย skill อีกตัว ให้เทียบ instruction กับ output ที่คนต้องการ แล้วถามว่า instruction ควรเป็นอย่างไรจึงได้ผลนั้น และสรุปเป็นข้อที่ยืดหยุ่นกว่า
  6. feedback loop รายวัน: Buzz ส่งข้อเสนอเข้า Slack channel พร้อมเหตุผล ทีมกด emoji บอกว่าทำอะไรจริง และเขียนโน้ตใน thread ได้ Buzz รันทุกวัน เทียบสิ่งที่เสนอกับสิ่งที่ทีมทำ แล้วเปิด pull request แก้ skill ใน Git repo ทีมรีวิวราว 60 วินาที
  7. ข้อสังเกต: ส่วนที่ยากที่สุดคือมนุษย์ ต้องทำให้ให้ feedback ง่ายที่สุดในเครื่องมือที่ใช้อยู่แล้ว และทำให้ agent เหมือนเพื่อนร่วมทีมที่มีชื่อกับบุคลิก ผู้พูดบอกว่ายังคงให้คน review/merge PR เพื่อไม่ให้ agent drift ไปทางแปลกๆ
  8. Buzz รันบน Oz ซึ่งเป็นแพลตฟอร์ม orchestration ของ Warp สำหรับ cloud agents ทริกเกอร์ด้วย schedule หรือ trigger คล้าย routines ที่เห็นในงานเมื่อวาน

ตัวเลข / ข้อเท็จจริงที่ผู้พูดบอก

ตามที่ผู้พูดอ้างในคลิป ไม่ได้ยืนยันกับแหล่งอื่น

  • Buzz ประกอบด้วยราว 15 skills แทบไม่มีโค้ด สร้างในไม่กี่วัน (ตามผู้พูด)
  • skill file สั้นลงราวหนึ่งในห้าหลังเปลี่ยนจาก rules เป็น principles
  • mentions ราวไม่กี่พันต่อเดือน ประมาณ 50% ถูก skip
  • cloud agent runs ไม่กี่พันครั้งต่อเดือน รันบน Oz
  • รีวิว PR ประจำวันใช้ราว 60 วินาที เพราะเป็นการแก้ภาษาอังกฤษไม่กี่บรรทัด
  • ผู้พูดอ้างว่า draft ของ Buzz ตัดงานออกราว 90% เหลือ 10% ที่มีค่าที่สุดให้คนทำ

ประโยคเด่น (ต้นฉบับ)

“The agent sort of needed to learn how to learn.”

agent ต้องเรียนรู้วิธีเรียนรู้ด้วย

“Think about how your agent will improve over time and not just how to nail that initial prompt.”

คิดว่า agent จะดีขึ้นตามเวลาอย่างไร ไม่ใช่แค่ทำ prompt แรกให้เป๊ะ

“The trickiest part of designing feedback loops is always the humans.”

ส่วนที่ยากที่สุดของการออกแบบ feedback loop คือมนุษย์เสมอ

สิ่งที่นำไปทำต่อ

  • เขียน skill เป็น principles ที่อธิบายว่าคิดอย่างไรและทำไม ไม่ใช่รายการ if-then ลองดูว่า skill สั้นลงและยืดหยุ่นขึ้นไหม
  • เพิ่ม skill ที่สอน agent ให้เทียบ instruction กับ output ที่ต้องการ แล้วสรุปเป็นหลักทั่วไป ไม่ใช่กฎเฉพาะเคส
  • เก็บ skills ใน Git แล้วให้ agent เปิด PR แก้ instruction รายวัน ให้คนรีวิวเร็วๆ เพื่อคุมการ drift
  • เก็บสัญญาณจากงานที่ทีมทำอยู่แล้ว เช่น emoji reaction กับ thread note ใน Slack ให้ภาระเพิ่มของคนน้อยที่สุด
  • ตั้งชื่อและบุคลิกให้ agent ให้ทีมรู้สึกเป็นเพื่อนร่วมงาน เพื่อให้ feedback มีคุณภาพ

ข้อควรระวังในสรุปนี้

  • transcript มาจาก Whisper large-v3 ที่ถอดเอง ชื่อเฉพาะอาจเพี้ยน เช่น 'Cloud Code' = Claude Code, 'scale file' ในไฟล์น่าจะหมายถึง skill file, 'Ralph loop' ตามที่ได้ยิน
  • ผู้พูดแนะนำตัวว่าชื่อ Petra และเป็นหัวหน้า developer experience ที่ Warp ไม่ได้บอกนามสกุล
  • ตัวเลขเช่น 50% skip, 90%/10% และจำนวน mentions/runs ต่อเดือนเป็นคำบอกของผู้พูด ไม่มีหลักฐานในคลิป และ 'few thousand' ฟังจาก ASR อาจไม่ตรงทุกจุด
  • คำว่า 'routines on the cloud code' ที่ผู้พูดอ้างถึงงานเมื่อวาน ไม่ได้อธิบายรายละเอียดในคลิปนี้
