Omni สร้าง agent วิเคราะห์ข้อมูล Blobby: บทเรียนจาก harness, semantic layer และ evals

Building the best agentic analytics harness: Powered by Claude, built with Claude Code

ผู้พูด: Chris Merrick (Cofounder and CTO, Omni (ตามคำอธิบายคลิป และผู้พูดบอกว่าตนเป็น CTO))

เหมาะกับ: วิศวกรที่สร้าง agent บนข้อมูลองค์กรหรือออกแบบ agent harness และอยากได้บทเรียนจากการแก้ปัญหาจริงผ่าน traces กับ evals

Chris Merrick CTO ของ Omni เล่าว่าทีม engineering ราว 25 คนใช้ Claude Code เร่งความเร็ว และสร้าง agent วิเคราะห์ข้อมูลชื่อ Blobby บน semantic layer ใน 18 เดือน บทเรียนหลักคือเพิ่ม context ในนิยามข้อมูล, ให้ agentic loop กู้จาก error ได้, รวม sub-agent กลับเข้า agent ตัวนอก (consolidating the brain) และให้ Claude เขียน SQL แล้ว parse แทนรูปแบบ JSON ที่คิดขึ้นเอง

Omni's CTO describes building the Blobby analytics agent over 18 months: richer semantic-layer context, error recovery, merging sub-agent tools into the outer agent, and letting Claude write SQL that Omni parses.

ประเด็นสำคัญ

  1. ผู้พูดบอกว่าทีม engineering ราว 25 คนเริ่มทดลองเครื่องมือ AI ต้นปี 2025 และจุดเปลี่ยนคือเมื่อ Claude Code กับโมเดล Opus ออก วิศวกรอาวุโสเริ่มเห็นว่าช่วยได้สม่ำเสมอ ความเร็วพุ่งหลังกลับมาจากช่วงวันหยุดปลายปี สะท้อนในกราฟ commit เข้า main ที่เขาเปิดให้ดู
  2. Omni ให้คุยกับข้อมูล: Claude แปลคำถามเป็น semantic query แล้วผ่าน semantic layer แปลงเป็น SQL รันบน warehouse เหตุผลคือ Claude ต้องรู้ธุรกิจและข้อมูลของคุณ (เช่น 'last quarter' หมายถึงต่างกันระหว่างทีม product กับทีม sales)
  3. semantic layer ทำสามอย่าง: รวมและคัดชุดข้อมูลในคลังที่มีนับหมื่นนับแสนตาราง, เก็บ context ไว้ข้างนิยามของ field นั้น (เทียบกับ Claude.md ที่วางใกล้โค้ด) และคุม permissions และมี feedback loop ให้คำถามถัดไปไหลกลับมาปรับนิยาม
  4. ยกระดับคุณภาพด้วย metadata สำหรับ LLM: ฟิลด์ AI context, sample queries และตัวอย่าง values ของ field (เช่น EMEA, NAM, APAC) ให้โมเดลอนุมานรูปแบบได้
  5. เพิ่ม agentic loop (สร้าง harness เอง มี tasks) แล้วพบว่าจุดที่เพิ่มคุณภาพมากที่สุดอย่างหนึ่งคือสอนให้ Blobby กู้จาก error พร้อมงบให้ลองใหม่ และลงทุนเขียน error message ที่บอกวิธีแก้ จากนั้นสลับ Haiku เป็น Sonnet เพราะบทสนทนาแบบ agentic ซับซ้อนและยาวขึ้น การใช้งานก็พุ่งตาม
  6. จากการดู traces ของเซสชันที่แย่ (เรียกว่า Blobotomies) พบว่า agent ตัวนอกวางแผนแต่ sub-agent สร้าง query ครั้งละหนึ่งอัน agent ตัวนอกไม่รู้ว่า query เดียวตอบอะไรได้บ้าง จึงแก้ด้วย 'consolidating the brain' ดึง tools ขึ้นมาไว้ที่ agent ตัวนอก ลดพฤติกรรมที่คาดเดายาก
  7. เปลี่ยนอินเทอร์เฟซสร้าง query จาก JSON ที่ออกแบบเอง มาเป็นให้ Claude เขียน SQL แล้ว parse (ฟื้นโค้ด SQL parser ที่เก็บไว้หลายปี) ได้ query ที่คุ้มกว่าในช็อตเดียวและไม่ต้องสอนรูปแบบเฉพาะ ผู้พูดว่า Claude ชอบเขียน CTE และ parser รองรับดี
  8. สถาปัตยกรรมปัจจุบัน: outer loop ทำ checkpoint เพื่อกู้จากความล้มเหลว, inner loop มี tools (dashboards, visualizations, validation, data modeling) และมีระบบ evals ภายใน กำลังทำสำหรับลูกค้าด้วย ผู้พูดชอบ evals เพราะได้ trace มาวิเคราะห์ และสรุปเป็น judge ได้ การเป็นผู้ใช้ Claude Code เองช่วยให้เข้าใจ harness ที่ดี เพราะ semantic model คล้าย codebase

ตัวเลข / ข้อเท็จจริงที่ผู้พูดบอก

ตามที่ผู้พูดอ้างในคลิป ไม่ได้ยืนยันกับแหล่งอื่น

  • ทีม engineering ราว 25 คน และมีลูกค้าหลายร้อยราย (ตามผู้พูด)
  • คำอธิบายคลิประบุว่า 99% ของโค้ดแพลตฟอร์มเขียนด้วย Claude Code แต่ตัวเลขนี้ไม่ได้ยินในส่วนที่ผู้พูดพูด
  • Blobby พัฒนามาราว 18 เดือน
  • คลังข้อมูลองค์กรจริงมีชุดข้อมูลหลักหมื่นถึงหลักแสน ตามที่ผู้พูดยกเป็นเหตุผลของ semantic layer
  • การเปลี่ยนจาก Haiku เป็น Sonnet ทำให้การใช้ token สูงขึ้นโดยตั้งใจ และการใช้งาน Blobby พุ่ง

ประโยคเด่น (ต้นฉบับ)

“You want to be careful not to have a split brain between any sort of sub-agent system and outer agent system.”

ระวังอย่าให้ระบบ sub-agent กับ agent ตัวนอกแยกสมองกัน

“Claude is incredible at answering questions, but you need to tell it more about your business if you want it to answer questions about your business”

Claude เก่งตอบคำถาม แต่ต้องบอกเรื่องธุรกิจของคุณเพิ่มถ้าอยากให้ตอบเรื่องธุรกิจคุณ

“being users of Claude Code helped us understand what a good harness looks like”

การเป็นผู้ใช้ Claude Code ช่วยให้เข้าใจว่า harness ที่ดีหน้าตาเป็นอย่างไร

สิ่งที่นำไปทำต่อ

  • ใส่ context ให้ LLM ไว้ข้างนิยามที่เกี่ยวข้อง (AI context, sample queries, ตัวอย่าง values) ไม่ใช่รวมไว้ที่เดียว
  • ให้ agentic loop มีงบลองใหม่เมื่อเจอ error และเขียน error message ให้บอกสาเหตุกับทางแก้
  • เมื่อคุณภาพไม่คงที่ ให้ดู traces ของเซสชันที่ล้มเหลว แล้วหา root cause เชิงสถาปัตยกรรม เช่น ความรู้ที่แยกระหว่าง agent ตัวนอกกับ sub-agent
  • ให้โมเดลใช้รูปแบบที่มันเก่งอยู่แล้ว (เช่น SQL) แทนคิดภาษาเฉพาะขึ้นมาให้ต้องสอน
  • เก็บ traces จาก evals ไว้ใช้ทั้งเป็น observability และสร้าง judge ต่อ
