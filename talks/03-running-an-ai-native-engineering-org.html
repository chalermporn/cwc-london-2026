บริหารทีมวิศวกรรมแบบ AI-native: คอขวดย้ายแล้ว กติกาทีมก็ต้องเขียนใหม่

Running an AI-native engineering org

ผู้พูด: Fiona Fung (Leads engineering and product for Claude Code and Cowork; เคยสร้างและนำทีมที่ Meta และ Microsoft)

เหมาะกับ: เหมาะกับ engineering manager และ tech lead ที่กำลังเปลี่ยนทีมให้ใช้ agentic coding เป็นค่าเริ่มต้น

Fiona Fung เล่าว่าพอการเขียนโค้ดไม่ใช่คอขวดอีกต่อไป กติกาทีมหลายข้อก็ค่อยๆ หมดประโยชน์โดยไม่มีใครรู้ตัว ทีม Claude Code เลยเขียนใหม่ทั้งเรื่องรีวิว วางแผน onboarding การจ้างงาน และ source of truth ข้อสรุปคือให้เน้นการ verify เน้น dogfooding และให้ทีมมีสิทธิ์ฆ่า process เก่าได้เสมอ

Fiona Fung explains how the bottleneck moved away from writing code at Anthropic and which team norms the Claude Code team rewrote (review, planning, onboarding, hiring, source of truth), with verification and dogfooding as the main themes.

ประเด็นสำคัญ

  1. คอขวดย้ายที่ ประโยคหลักคือ 'what served you prior may no longer' ตอนก่อนนี้ bandwidth ของวิศวกรแพง ทุกอย่างเลยหมุนรอบการปกป้องมัน (วางแผนเยอะ รีวิวเยอะ) แต่ตอนนี้การเขียนโค้ด เขียนเทสต์ และ refactor ไม่ใช่ส่วนที่ช้าแล้ว
  2. คอขวดใหม่คือ verification, ใครรีวิว และ maintenance เธอเล่าว่า TDD ที่เคยเหมือนกินบรอกโคลีกลับสนุกขึ้นเมื่อให้ Claude เขียนเทสต์ก่อน
  3. ถกเถียงเชิงเทคนิค 'code wins' ไม่ต้องขึ้นไวต์บอร์ด ให้สร้างหลายเวอร์ชันของ PR มาเทียบกัน ลด design doc ยาวๆ คุยกันใน PR หรือ prototype แทน และ prototype ก็ขยายไปสู่ production ได้เร็วขึ้น
  4. รีวิวโค้ด Claude เก่งเรื่อง style, lint, bug ชัดๆ และตรวจ spec drift (แนะนำให้เช็ค spec เข้า codebase) แต่ต้องมีคนในลูปสำหรับเรื่องกฎหมาย risk tolerance trust boundary รวมถึง product sense และ taste
  5. โครงทีม: roles กำลังเบลอ เธอเน้น 2 โปรไฟล์ คือ creative builders ที่มี product sense กับคนที่มี deep system expertise manager ทุกคนในทีม Claude Code เริ่มจากเป็น IC ก่อน และ product sense สร้างจาก dogfooding ('ant food')
  6. Source of truth คือ codebase: ใช้ Claude ทำ tech deep dive ตอน onboard และถ้ามี spec ให้แปลงเป็น skill ที่เช็คเข้า codebase จะได้ไม่ล้าสมัย
  7. การ rollout: กติกาที่ต้องตรงกันทั้งทีม (ทุกคนใช้ Claude Code/Cowork, Claude-ify ทุกอย่างที่ทำได้, มีสิทธิ์ฆ่า process เก่าอย่างชัดแจ้ง) กับพื้นที่ให้แต่ละ pod ปรับเองจากล่างขึ้นบน
  8. สัญญาณว่าได้ผล: onboarding ramp-up ลดลง, PR cycle time ลดลง (แต่ให้แตกเป็นช่วงดูว่าคิว CI/build ไม่ติด), commit ที่มี Claude ช่วยเพิ่มขึ้น และต้องวัดผลลัพธ์ผลิตภัณฑ์ด้วย ไม่ใช่แค่ throughput คำถามที่ยังเปิดอยู่: ต้องแยกทีม iOS/Android ไหม และจะ automate รีวิวไปไกลแค่ไหน

ตัวเลข / ข้อเท็จจริงที่ผู้พูดบอก

ตามที่ผู้พูดอ้างในคลิป ไม่ได้ยืนยันกับแหล่งอื่น

  • เธอบอกว่าแทบทุก commit ใน Claude Code ตอนนี้ co-authored โดย Claude (ไม่เห็น commit ที่ไม่ใช่มาหลายเดือน)
  • ตัวอย่างอดีต: ตอนอยู่ Visual Studio ต้อง merge ได้ทีละ 6 PR เพราะคิว build เป็นคอขวด
  • ตัวชี้วัดที่แนะนำ: onboarding ramp-up time (เวลาจนวิศวกรส่ง PR แรก), PR cycle time, สัดส่วน Claude-assisted commits

สิ่งที่นำไปทำต่อ

  • เลือก workflow หรือการประชุมที่เสียแรงมากที่สุดมาหนึ่งอย่าง แล้วถามว่ายังตอบเป้าหมายเดิมไหม มี part ไหนให้ Claude ช่วยได้
  • ทบทวน process ที่สะสมไว้ (SLA, design doc, ขั้นรีวิว) และให้ทีมมีสิทธิ์ยกเลิกอย่างเป็นทางการ
  • ลงทุนกับ verification แบบ shift left: เช็ค spec เข้า repo, ใช้ automated review แต่คงคนไว้ที่ trust boundary
  • ย้าย source of truth ไว้ใน codebase (เช่น spec เป็น skill) และใช้ Claude ช่วย onboard คนใหม่
  • เวลาวัดผล PR cycle time ให้แยกช่วง ไม่งั้นอาจเข้าใจผิดว่า adoption ไม่ได้ผล ทั้งที่คอขวดย้ายไปอยู่ที่ CI
