AirOps ไล่แก้จุดฝืด ทำ agent ให้นักการตลาดใช้ได้จริงด้วย Claude Agent SDK

How AirOps chases friction to build AI products with Claude

ผู้พูด: Dylan (Product team, AirOps)

เหมาะกับ: ทีมโปรดักต์และวิศวกรที่ต้องส่ง agent เข้า workflow ของคนสายอาชีพที่ไม่ใช่นักพัฒนา และสนใจเรื่อง harness, sub-agent และ governance

Dylan จาก AirOps เล่าการเปลี่ยนจาก workflow builder แบบ node ไปเป็น agent ชื่อ Quill และ Playbooks บน Claude Agent SDK กับ Managed Agents สำหรับนักการตลาดเนื้อหา โดยแก้สองจุดฝืดคือให้เข้ากับ workflow เดิมของคน (เอกสาร ความโปร่งใส human review) และทำ harness ให้คุณภาพสม่ำเสมอ (specialized tools กับ sub-agents) บทเรียนใหญ่คือจุดฝืดย้ายที่ไปเรื่อยๆ ต้องไล่ตามต่อ

AirOps moved from a node-based workflow builder to Claude-powered agents (Quill, Playbooks, Inbox), fitting marketers' document-based workflow with human review and using specialized tools and sub-agents for quality.

ประเด็นสำคัญ

  1. AirOps เป็นแพลตฟอร์ม growth marketing สำหรับ AI search (คล้าย SEO แต่สำหรับ ChatGPT, Gemini, Claude) ช่วยแบรนด์เห็นตำแหน่ง หาช่องว่าง สร้างหรืออัปเดตคอนเทนต์ และวัดผล ก่อนหน้านี้ใช้ workflow builder แบบลาก node ซึ่งชนเพดานความซับซ้อน ต้องสอนเรื่อง liquid text กับ JSON ให้นักการตลาด และโมเดลใหม่ออกทีก็ต้องไล่แก้ทุก step
  2. จุดหักเหคือ Opus 4.5 ที่เก่ง tool calling และทำตามคำสั่ง ทีมลองให้ LLM คอมไพล์เอกสารเป็น workflow (เปราะ) และ agent orchestration framework แบบเดิม (เปลี่ยนการ route ต้องแก้โค้ด) จึงลงทุนกับ Claude Agent SDK ที่คุม agent ผ่านไฟล์ markdown และ skills แทนโปรแกรม
  3. ผลิตภัณฑ์ที่เพิ่งเปิดตัวชื่อ AirOps Next ประกอบด้วย Quill (agent ผู้ช่วยหลัก เข้าถึงข้อมูล AI search และ brand kit) กับ Playbooks (ประสบการณ์สร้างแบบเอกสาร ใกล้เคียง skill มี collaboration, governance, versioning) รวมถึง Inbox และ grid ผู้พูดอ้างกรณีลูกค้า Parallel ที่ได้ผลดีขึ้นและขึ้นระบบเร็วขึ้น
  4. จุดฝืดแรก ต้องเข้ากับ workflow ที่นักการตลาดทำอยู่ ผู้พูดว่า use case ไม่จำกัดบังคับให้ต้องตั้งใจเลือก โฟกัส 'marketers' เอกสารคือสิ่งที่คุ้นเคย (ไม่ใช่ node) ต้องโปร่งใสว่าใช้ tool อะไรตอนไหน มีการควบคุม และบังคับ human review ระหว่างทางไม่ใช่แค่รีวิว PR ตอนจบแบบงานโค้ด
  5. เดโม Playbook สั่งด้วย slash command กำหนด input/output/tools เพิ่ม MCP ใดก็ได้ ตั้ง trigger ตามเวลา webhook หรือ monitor (ร่วมกับ Parallel) และ insights เมื่อ metric ตก ในส่วน outline มอบหมายผู้รีวิวที่เท่านั้นที่ปลดบล็อก agent ได้ ผลโผล่ใน Inbox (ดู thought traces) และ grid ที่รีวิวระดับสเกล
  6. จุดฝืดที่สอง ความสม่ำเสมอของคุณภาพ ผู้พูดเปรียบ harness เป็นรถ โมเดลคือเครื่องยนต์ ส่วนที่เหลือที่สร้างรอบๆ ก็สำคัญมาก เน้นสองส่วนคือ tools กับการจัดการ context โดย Agent SDK และ Managed Agents API ช่วยให้ iterate เร็ว
  7. specialized tools: แทนที่ agent จะไล่ใช้ primitive tools เป็นสิบๆ ครั้งเพื่อวิเคราะห์ว่าหน้าเว็บมีปัญหาอะไร ก็ทำ tool เดียวที่รับ URL แล้วคืนข้อมูลหน้านั้น content gaps เทียบคู่แข่ง keyword และ prompt เป้าหมาย รวมถึง tool เทียบหน้ากับหน้าที่ติดอันดับ เป็นแนวคล้าย code mode
  8. sub-agents: เริ่มจาก Claude ตัวเดียวแล้วค่อยเพิ่มเมื่อเจอจุดบกพร่อง มี compliance check (ให้คะแนนตามกฎแบรนด์), writing (context โฟกัส ไม่ปนงานวิจัย), brand kit ที่ดึง context ต้น run เก็บเป็น artifact ให้ทุกส่วนอ้างอันเดียวกัน และ custom sub-agent ให้ solutions architect สร้างเอง ผู้พูดย้ำว่า context window ใหญ่ขึ้นไม่ได้แปลว่าควรใช้เต็ม

ตัวเลข / ข้อเท็จจริงที่ผู้พูดบอก

ตามที่ผู้พูดอ้างในคลิป ไม่ได้ยืนยันกับแหล่งอื่น

  • ผู้พูดบอกว่ากรณีลูกค้า Parallel ได้ citation rate เพิ่ม 130% และ share of voice เพิ่ม 42% และขึ้นระบบได้ใน 1 สัปดาห์ จากปกติราวหนึ่งเดือนด้วย workflow builder
  • specialized tool ลดการใช้โทเค็นราว 8% (ตัวเลขจาก ASR ผู้พูดพูดว่า 'an 8% decrease in like fewer tokens consumption') เมื่อเทียบกับการเรียก primitive tools วนหลายรอบ
  • ก่อนมี tool เดียว agent เรียก tool ราว 20 ครั้งเพื่อดึง context ที่ต้องการ
  • ลูกค้า enterprise 10 รายในช่วง beta เริ่มเผยแพร่คอนเทนต์ได้ภายในไม่เกิน 2 สัปดาห์
  • Opus 4.5 คือจุดที่ทีมตัดสินใจลงทุน agent หนักขึ้น และผู้พูดยกตัวอย่าง Opus 4.7 ที่มี context window 1 ล้านโทเค็น

สิ่งที่นำไปทำต่อ

  • ถ้าผู้ใช้ไม่ใช่นักพัฒนา ให้ห่อ skill เป็นรูปแบบที่เขาคุ้น เช่น เอกสาร แล้วเพิ่มความโปร่งใสว่าใช้ tool อะไร พร้อม versioning และ governance
  • บังคับ human review ระหว่างทางด้วยการมอบหมายผู้รีวิวต่อ section ที่ปลดบล็อก agent ได้ และมีกล่องข้อความ (inbox) รวมงานรอรีวิว
  • งานที่ agent ทำซ้ำบ่อย ให้รวมเป็น specialized tool ตัวเดียวแทนการให้ไล่ primitive tools ทีละตัว เพื่อลดโทเค็นและความเร็ว
  • เริ่มจากเอเจนต์ตัวเดียว แล้วแตก sub-agent เฉพาะเมื่อคุณภาพติดขัด (compliance, writing, brand context) และดึง context ที่ใช้ร่วมกันครั้งเดียวเก็บเป็น artifact
  • อย่าเติม context เต็ม window แม้โมเดลจะรองรับ และเตรียมแผนวัดผลเมื่อเปลี่ยน harness โดยไม่พึ่ง vibes

ข้อควรระวังในสรุปนี้

  • ASR เขียนชื่อบริษัทเป็น 'AerOps' และ 'Ahrefs Next' ในบางจุด ชื่อที่ถูกคือ AirOps / AirOps Next ตามชื่อคลิปและคำพูดส่วนใหญ่
  • ผู้พูดแนะนำตัวว่าชื่อ Dylan อยู่ product team ไม่มีนามสกุล และตัวเลขทั้งหมดเป็นข้ออ้างของผู้พูดเอง ไม่มีหลักฐานแนบในคลิป
  • ตัวเลข 8% ลดโทเค็นฟังจาก ASR ไม่ชัดว่าเป็นการลดของอะไรแน่ และเรื่อง Opus '46, 47' เป็นการพูดรวบรุ่นที่ ASR เขียน
  • ชื่อลูกค้าบางราย (เช่น 'Animal' และ 'Rock Content') ฟังจาก ASR อาจเพี้ยน จึงไม่ได้ใส่เป็นข้อเท็จจริง
  • ผู้พูดอ้างถึง 'AO insights' ซึ่งชื่ออาจเพี้ยนจาก ASR และเอ่ยถึง talks ก่อนหน้าเรื่อง dreaming sequences ซึ่งไม่ใช่ส่วนของคลิปนี้
