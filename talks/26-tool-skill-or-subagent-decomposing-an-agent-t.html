แยก agent ที่ prompt บวมให้ลงตัว: อะไรควรเป็น tool, skill หรือ subagent

Tool, skill, or subagent? Decomposing an agent that outgrew its prompt

ผู้พูด: Will (Engineering team, Applied AI, Anthropic (ได้ยินแค่ชื่อต้น))

เหมาะกับ: คนที่มี agent ใช้งานจริงแล้ว prompt กับ tool ยาวขึ้นเรื่อยๆ และกำลังสงสัยว่าควรแยกส่วนไหนเป็นอะไร (ควรรู้จัก skills, subagents, evals มาบ้าง)

เวิร์กชอปรับช่วง StockPilot ซึ่งเป็น inventory agent ที่ system prompt บวมถึง 400 บรรทัดและ eval ตก แล้วค่อยๆ แยกใหม่บน Claude Managed Agents โดยย้าย business logic ไปเป็น skills ลด tool เหลือ bash/read/write และเก็บ subagent ไว้เฉพาะ forecasting ผู้พูดรายงานว่าคะแนน eval ไต่ถึงราว 92% พร้อมใช้ token และต้นทุนน้อยลง

Decomposing a bloated 400-line-prompt inventory agent on Managed Agents: logic into skills, tools down to bash/read/write, one native subagent kept, hill-climbing evals to about 92%.

ประเด็นสำคัญ

  1. ปัญหาที่พบบ่อย: agent ที่ใช้ได้ดี พอเพิ่มความต้องการทีละนิด prompt ก็ยาวเป็นหลายร้อยบรรทัด มี tool กับ subagent เป็นโหล แล้ว performance ที่เคยดีก็ถดถอย StockPilot ตัวอย่างมี prompt ราว 400 บรรทัด 12 tools (3 ตัวเป็น wrapper ของ subagent)
  2. eval suite มี 12 งาน 5 ชนิด grader (รหัส R = regression งาน single-turn, F = failure mode งาน multi-turn) ผสม deterministic (turn count, latency, token) กับ LLM-as-judge (tone, คุณภาพ output) ผู้พูดทำ triage ผล eval ด้วย Claude Code ได้สาเหตุเป็นกลุ่มๆ
  3. รากของความล้มเหลวคือ context ไม่ใช่โมเดล เช่น R8 ที่ agent ดึง promo multiplier ถูก (3.1x) แต่ตอนคำนวณกลับใช้ 1.35 เพราะ policy สองจุดใน prompt ขัดกัน, F1 ไปถึงคำตอบถูกแต่ทางอ้อม, F2 พังที่การสื่อสารระหว่าง subagent กับ orchestrator
  4. ขั้น skills: เอา policy กับ procedure ออกจาก system prompt ไปเป็น skills เพื่อ progressive disclosure ผู้พูดบอกว่า prompt เหลือสั้นลงมาก และหลักคือ system prompt เก็บเฉพาะสิ่งที่ Claude ต้องรู้ทุกงาน ส่วนที่ใช้บางงานให้เป็น skill
  5. ขั้น tools: เริ่มจาก primitive แบบมนุษย์ (code execution, file system, web search, to-do list) แล้วเพิ่ม custom tool เมื่อจำเป็น อย่ารีบไป MCP ให้ใช้ MCP เมื่อมีชุด tool ที่หลาย client ใช้ร่วมกันและต้อง govern ใน Managed Agents primitive พวกนี้มีให้ในตัว
  6. ผลของการให้ code execution แทนอ่าน CSV เข้า context: token ต่อ task ลดจากกว่า 200,000 อย่างมาก ต้นทุนและเวลารันก็ลด ผู้พูดเตือนว่าไม่ได้ดีขึ้นทุกกรณี บางเคสอาจถดถอย
  7. ขั้น subagents: ใช้ในสองกรณีหลัก คือ (1) ต้องการ Claude หลายตัวช่วยขนานกัน เช่น research, code exploration (2) ต้องการสายตาใหม่ที่ไม่มี context เดิม เช่น code review และ forecasting ใน StockPilot ซึ่งถูกเก็บไว้เป็น subagent เดียว ใช้ callable agents แบบ native ของ Managed Agents แทนการห่อเป็น tool
  8. ผู้พูดบอกว่าหลายลูกค้ากำลังยุบ subagent กลับเข้า orchestrator เพราะโมเดลระดับ frontier จัดการข้อมูลได้มากขึ้นแล้ว
  9. สถาปัตยกรรมปลายทาง: orchestrator เดียวบน Managed Agents, 3 tools (bash, read, write), system prompt ราว 15 บรรทัด, business logic อยู่ใน skills, subagent forecasting หนึ่งตัว และ eval ไต่ขึ้นราว 92% จากหลักคิด hill climbing (วัด baseline แก้ architecture รัน eval ซ้ำ) พร้อมเตือนให้ปรับ eval ตามความสามารถที่เพิ่มขึ้น

ลำดับขั้นที่ทำในคลิป

  1. clone repo เวิร์กชอป เข้าโฟลเดอร์ agent decomposition แล้วรัน uv sync
  2. ก๊อป env example เป็นไฟล์ .env แล้วใส่ API key จาก Claude console
  3. รัน baseline ด้วย uv run evals --agent before (agent ฉบับ Messages API ในโฟลเดอร์ before)
  4. ถ้าอยากดูฉบับ Managed Agents ให้ดูโฟลเดอร์ starter และ deploy ด้วย uv run deploy starter
  5. ใช้ Claude Code รัน eval แล้วให้ช่วย triage หาสาเหตุเป็นธีม (โมเดลทำงานที่ควรเป็น tool, โครงสร้าง output ไม่ถูกบังคับ, policy ขัดกันใน prompt)
  6. ขั้น skills: ให้ Claude วิเคราะห์ agent.py และย้ายส่วนของ system prompt ไปเป็น skills
  7. ขั้น tools: ยุบ tool เฉพาะกิจ เหลือ primitive (bash, read, write) แล้ว redeploy ไป Managed Agents
  8. รัน eval ซ้ำ (เช่น F1) เพื่อเทียบ token, cost, เวลา ก่อนและหลัง
  9. ขั้น subagents: ถอด wrapper-subagent ที่ไม่จำเป็น เก็บ forecasting ไว้ แล้วเปลี่ยนมาใช้ callable agents ของ Managed Agents
  10. ทบทวนสถาปัตยกรรมสุดท้ายและคะแนน eval รอบสุดท้าย

ตัวเลข / ข้อเท็จจริงที่ผู้พูดบอก

ตามที่ผู้พูดอ้างในคลิป ไม่ได้ยืนยันกับแหล่งอื่น

  • ก่อนแก้: system prompt ราว 400 บรรทัด, 12 tools (3 ตัวคือ wrapper ของ subagent)
  • คะแนน eval ตั้งต้นที่ผู้พูดบอกในสไลด์ราว 83% แต่ตอนรันจริงในเดโมได้ 62% (ผ่าน 7 จาก 12)
  • ระหว่างทาง: prompt จาก 400 บรรทัดเหลือราว 50 บรรทัด พอจบสุดเหลือราว 15 บรรทัด
  • หลังแก้: tools เหลือ 3 (bash, read, write) และคะแนน eval ราว 92%
  • token ต่อ task ก่อนแก้เกิน 200,000 แล้วลดลงมากหลังให้ code execution (ผู้พูดไม่ได้อ่านตัวเลขหลังแก้ชัดเจน)
  • ตัวอย่างบั๊ก R8: baseline 12 units ต่อวัน, promo multiplier 3.1x แต่ agent คำนวณด้วย 1.35
  • ผู้พูดใช้ Opus 4.7 กับ effort ระดับ extra high ใน Claude Code เป็นค่าประจำ

ประโยคเด่น (ต้นฉบับ)

“Leave the system prompt only for the information that Claude needs in its mind, regardless of the task that you give it”

system prompt เก็บเฉพาะสิ่งที่ Claude ต้องรู้ไม่ว่าจะได้งานอะไร

“whenever we build agents, we lean into human-like primitives first”

เวลาสร้าง agent เราเริ่มจาก primitive แบบมนุษย์ก่อนเสมอ

“it's important to make sure that your evals are updated as your product capability expands”

ต้องอัปเดต eval ให้ทันตามความสามารถของผลิตภัณฑ์ที่เพิ่มขึ้น

สิ่งที่นำไปทำต่อ

  • ถ้า system prompt ยาวเกินร้อยบรรทัด ลองแยกกฎที่ใช้เฉพาะบางงานไปเป็น skills ก่อน แล้ววัด eval เทียบ
  • ก่อนเขียน custom tool ใหม่ ถามว่า bash กับ file system ทำแทนได้ไหม โดยเฉพาะงานวิเคราะห์ข้อมูล
  • ใช้ MCP เมื่อมีหลาย client ต้องใช้ชุด tool เดียวกันและต้อง govern เท่านั้น
  • ใช้ subagent เมื่อต้องการขนานหรือต้องการสายตาใหม่ที่ไม่ปนกับ context หลัก และดูการสื่อสารระหว่าง orchestrator กับ subagent เป็นจุดเสี่ยง
  • ตั้ง eval เป็น baseline ก่อนแก้ทุกครั้ง แก้ทีละอย่างแล้วรันซ้ำ และให้ Claude Code ช่วย triage ผล

ข้อควรระวังในสรุปนี้

  • ชื่อผู้พูดได้ยินแค่ Will ไม่มีนามสกุล
  • ตัวเลขคะแนน eval ตั้งต้นไม่ตรงกัน: สไลด์พูดราว 83% แต่เดโมได้ 62% (7 จาก 12) ต้องอ้างทั้งสองค่าตามที่ผู้พูดบอก
  • ผู้พูดบอกก่อนว่าใช้ sub agent สามตัวเป็น tool และพูดว่า prompt เหลือราว 50 บรรทัดระหว่างทางกับราว 15 บรรทัดตอนสุดท้าย ตัวเลขตามคำพูดจาก ASR
  • ตัวเลข token หลังแก้ไม่ได้อ่านออกเสียง รู้แค่ว่าลดลงมาก
  • เวิร์กชอปเกี่ยวกับ callable agents ของ Managed Agents ผู้พูดไม่ได้อธิบายพารามิเตอร์ API
  • ผลทั้งหมด (92%, ลด token) เป็นผลของเดโมกรณีเดียว ผู้พูดเตือนเองว่าไม่ได้ดีขึ้นทุกครั้ง
