#06 · คีย์โน้ต · 26:25

เส้นโค้งความสามารถของโมเดล และวิธีขี่ไปกับมัน

The capability curve

ผู้พูด: Jeremy (Product Manager ที่ Anthropic ทำงานกับทีม research ดูแลเรื่อง coding behaviors และ capabilities (ผู้พูดแนะนำตัวเองด้วยชื่อแรกเท่านั้น))

เหมาะกับ: developer ที่สร้างแอปหรือ agent บน Claude และอยากรู้ว่าต้องปรับวิธีทำงานอย่างไรเมื่อโมเดลใหม่ออกมาทุกไม่กี่เดือน

ผู้พูดไล่ให้เห็นว่าโมเดลเก่งขึ้นเร็วแค่ไหนในรอบ 12 เดือน ผ่านสามเรื่องหลัก คือ วางแผนก่อนลงมือ กู้คืนจาก error และรักษาสมาธิในงานยาว แล้วสรุปเป็นแนวปฏิบัติสำหรับ developer ว่า ต้องมี evals ที่เชื่อถือได้ ลด scaffolding ลง เปิดพื้นที่ให้โมเดลทำงาน และปิด loop ให้ agent ช่วยปรับปรุง agent ด้วยกันเอง

Anthropic's Jeremy traces how models improved in a year (planning, error recovery, long-run coherence) and gives developers four habits to ride the curve: trusted evals, shrinking scaffolding, giving the model room to work, and closing the agent loop.

ประเด็นสำคัญ

  1. ผู้พูดเล่าว่าเมื่อปีก่อน Opus 4 ยังเป็น state of the art และ Claude Code เพิ่งเปิดตัว ตอนนี้ coding agent เปลี่ยนวิธีทำซอฟต์แวร์ไปเกือบหมด ถามผู้ฟังแล้วราวครึ่งห้องเคย ship PR ที่ Claude เขียนทั้งหมดในสัปดาห์ที่ผ่านมา
  2. SWE-bench Verified เคยอยู่ราว 60% ตอน Sonnet 3.7 และ Opus 4.7 ผ่าน 87% ผู้พูดบอกว่าโมเดลระดับ frontier ภายใน (Mythos Preview) อิ่มตัว benchmark นี้จนไม่ใช้วัดแล้ว คอขวดจึงย้ายจากการแก้ PR ไปที่เรื่องอื่น
  3. เดโมให้ Claude สร้างเว็บ Claude.ai ใหม่ในครั้งเดียว Sonnet 4 เขียน 2,000 บรรทัดแต่ chat ไม่ตอบ ส่วน Opus 4.7 เขียนราว 1,700 บรรทัด ได้แอปที่ chat ใช้งานได้ มี sidebar ประวัติ แผนภาพ mermaid และ dark mode
  4. ความก้าวหน้าสามด้าน ได้แก่ วางแผนและให้เหตุผลก่อนลงมือ (ไม่ต้อง scaffold บังคับ แค่ตั้ง reasoning effort สูง) กู้คืนจากความล้มเหลวจน doom looping แทบหายไป และรักษา coherence ได้ถึง 1 ล้าน token หรือมากกว่า ทำให้ไม่ต้องหั่นงานเป็นชิ้นเล็กหรือคอยเฝ้า
  5. รวมสามด้านแล้วได้ long-horizon agent ที่รันได้หลายชั่วโมง ตัวอย่างที่ผู้พูดเล่าคือผู้ก่อตั้ง Bun ให้ Claude เขียน JavaScript engine ของ Bun ใหม่เป็น Rust ภายในหนึ่งสัปดาห์ จนเกือบผ่าน test suite ครบ เพราะ Bun มี test suite coverage เกือบ 100% คอยตรวจ
  6. Evals คือ unit test และ regression test ของยุค AI ควรสร้างให้ตรงกับ traffic จริงแทนใช้ academic benchmark และต้องรู้ว่าเมื่อไหร่ eval อิ่มตัว (เช่นโมเดลได้ 90% แล้วที่เหลือทำไม่ได้) มิฉะนั้นจะมองไม่เห็นว่าโมเดลใหม่ดีขึ้น ทีมที่มี evals ปรับตัวกับโมเดลใหม่ได้เร็วกว่า
  7. ให้ลด scaffolding (prompt, tools, harness) ลงเมื่อได้โมเดลใหม่ เพราะ prompt ยาวสะสมคำสั่งที่ออกแบบกับข้อบกพร่องของโมเดลเก่า ผู้พูดยกตัวอย่างตัวอย่าง citation format เก่าใน prompt ของ Claude.ai ที่โมเดลใหม่ทำตามจนผิดรูปแบบ พอแก้ไม่กี่ตัวอักษรก็หายทั้งกลุ่ม
  8. ให้พื้นที่โมเดลทำงาน คือเปิด adaptive thinking และตั้ง effort สูง ปล่อยให้ทำงานแบบอัตโนมัติอย่างควบคุมได้ด้วย Auto Mode ที่มี classifier ตรวจทุก tool call และปิด loop ให้ Claude Code รัน eval ของ agent แล้วช่วยปรับ prompt กับ tools เอง

ตัวเลข / ข้อเท็จจริงที่ผู้พูดบอก

ตามที่ผู้พูดอ้างในคลิป ไม่ได้ยืนยันกับแหล่งอื่น

  • SWE-bench Verified: Sonnet 3.7 ราว 60% เมื่อปีก่อน เทียบกับ Opus 4.7 ผ่าน 87% ผู้พูดสรุปว่าแก้ issue ได้มากขึ้นราว 3 เท่า
  • เดโมสร้าง Claude.ai: Sonnet 4 ราว 2,000 บรรทัด เทียบกับ Opus 4.7 ราว 1,700 บรรทัด
  • โมเดลรักษา coherence ได้ถึง 1 ล้าน token และมากกว่านั้นตามที่ผู้พูดบอก (แต่ยังไม่สมบูรณ์เมื่อถึงหลายล้าน token)
  • เคส Bun เขียนใหม่เป็น Rust ใช้เวลาประมาณ 1 สัปดาห์ ผ่าน test suite เกือบ 100% ซึ่งผู้พูดบอกว่าถ้าทำเองจะใช้หลายเดือน
  • ตัวอย่าง eval อิ่มตัว: Opus 4.7 ทำได้ 90% แล้วอีก 10% ที่เหลือไม่มีโมเดลไหนทำได้ (ผู้พูดยกเป็นตัวอย่างสมมติ)
  • ตัวอย่าง prompt แบบ Frankenstein ราว 3,000 บรรทัดที่สะสมจากการแก้ failure ของโมเดลเก่า

ประโยคเด่น (ต้นฉบับ)

“evaluations are just the unit tests and the regression tests of the AI era.”

evals ก็คือ unit test กับ regression test ของยุค AI

“you want to cut down your prompt, figure out what's not necessary anymore, and describe what you actually intend for your application”

ตัด prompt ให้สั้นลง หาว่าอะไรไม่จำเป็นแล้ว แล้วบอกเจตนาจริงของแอปแทน

“you don't want it to delete your cluster or deploy jobs to prod without you asking.”

ไม่อยากให้มันลบ cluster หรือ deploy ขึ้น prod เองโดยไม่ถามก่อน

สิ่งที่นำไปทำต่อ

  • สร้าง eval ชุดแรกจาก failure mode และ traffic จริงของแอปตัวเอง ไม่ต้องรอให้สมบูรณ์ แล้วใช้รันเทียบโมเดลใหม่ทันทีที่ออก
  • เช็กว่า eval ที่ใช้อยู่อิ่มตัวหรือยัง ถ้าโมเดลใหม่ได้คะแนนเพิ่มแค่ 1% ให้ลองเพิ่มความยากก่อนสรุปว่าโมเดลไม่ดีขึ้น
  • ทบทวน system prompt ทุกครั้งที่เปลี่ยนโมเดล ลองตัดให้เหลือน้อยที่สุดแล้วใช้ evals ยืนยันว่าคุณภาพไม่ตก
  • ตั้ง effort สูงและเปิด adaptive thinking ในงานที่ต้องการความฉลาด แล้วลดการบังคับให้วางแผนเอง
  • ให้ Claude Code รัน eval ของ agent ตัวเองเพื่อเสนอการปรับ prompt และ tools แทนการแก้ทีละจุดด้วยมือ
