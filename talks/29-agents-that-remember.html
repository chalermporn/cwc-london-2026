agent ที่จำข้าม session ได้: memory store กับ dreaming

Agents that remember

ผู้พูด: Kevin (Engineer, Anthropic (ได้ยินแค่ชื่อต้น))

เหมาะกับ: คนที่เคยรู้จัก agent, environment, session ของ Managed Agents แล้ว และอยากให้ agent จำข้าม session ได้

เวิร์กชอปต่อ memory store (ที่เก็บแบบ file system ที่ mount เข้า session) ให้ agent บน Managed Agents จำข้อมูลข้าม session ได้ แล้วใช้ dreaming เป็น batch job แบบ multi-agent ที่ตรวจ จัดระเบียบ และยุบข้อมูลซ้ำใน memory เพื่อไม่ให้บวม ผู้พูดสาธิตเปรียบเทียบ agent ก่อนมี memory, หลังมี memory และหลัง dream

Wiring persistent memory stores onto Managed Agents sessions, then using dreaming, an async multi-agent batch job, to fact-check, organize and deduplicate the memory into a new output store.

ประเด็นสำคัญ

  1. ปัญหาตั้งต้น: session ของ agent แยกกัน ข้อมูลที่บอกใน session หนึ่งไม่ไปถึงอีก session เดโมแสดงว่าถามซ้ำใน session ใหม่ agent ตอบไม่ได้
  2. เพิ่ม concept ใหม่สองตัวต่อจาก agent, environment, session คือ memory store (ที่เก็บแบบ file system แนบเป็น resource ของ session) กับ dream (job แบบ async ที่เรียบเรียง memory จาก transcript เก่า)
  3. memory store mount เป็น file system ใน container ของ session โมเดลมี tool อ่านเขียนและใช้ bash, grep สำรวจได้ จะสร้างกี่ store ก็ได้ แบ่งตามผู้ใช้หรือ workspace ได้ตามต้องการ
  4. ตอนสร้าง store ใส่ชื่อกับคำอธิบาย ตอนแนบเข้า session ส่ง memory store ID พร้อม prompt ชี้นำว่าควรจดอะไร และ field access (ค่าเริ่มต้นอ่านเขียน ตั้งเป็นอ่านอย่างเดียวได้) เดโมแสดง agent ไปอ่าน memory ก่อน แล้วบันทึกลงไฟล์ sessions.md ในรอบถัดไปก็ grep หาเจอ
  5. ไฟล์ memory มีเวอร์ชัน แก้ทีไรสร้างเวอร์ชันใหม่ มี endpoint ให้ list และตรวจ และใน console ดูแก้ไฟล์เองได้ เช่น แก้เมื่อ Claude เขียนผิด
  6. ปัญหาของ memory เฉยๆ: agent มักเทข้อมูลลง store ไปเรื่อยๆ จนบวม ไม่เป็นระเบียบ และมีข้อมูลเก่า dreaming จึงเป็น batch process ที่รันแบบ async ผ่าน API หรือ console ด้วย harness แบบ multi-agent
  7. การสร้าง dream job: เลือกโมเดล (Opus 4.7 หรือ Sonnet 4.6 ตามคุณภาพกับต้นทุน) ใส่ input memory store กับรายการ session ID (ตัวอย่างบอกประมาณ 10 ถึง 20 ได้ สูงสุดราว 100 และกำลังขยาย) และ instructions เสริมได้ แล้วจะได้ dream ID กลับมา
  8. dream ไม่แตะ store ต้นฉบับ แต่โคลนเป็น output memory store แล้วแก้ที่นั่น (non-destructive) ในเดโมได้ไฟล์ index ที่ชี้ไปยังไฟล์ memory, ไฟล์ event logistics ที่เพิ่มรายละเอียด และไฟล์เดิมถูกจัดรูปใหม่ มี diff ใน console ให้ตรวจ
  9. dreaming สร้างบน primitive ของ Managed Agents เอง จึงเปิดดู session ของ dream ได้ ภายในมี orchestrator เปิด subagent หนึ่งตัวต่อ session อินพุต ตั้งใจให้ exhaustive แล้ว session ใหม่ที่ใช้ output store อ่าน index ก่อนและตอบได้ละเอียดขึ้นมาก
  10. ภาพรวมเป็นสามชั้นที่ประกอบกันได้: session (ชั่วคราว) memory store (เชื่อมข้าม session) dreaming (จัดระเบียบ ปรับปรุง memory ให้คงขนาดที่จัดการได้และไม่ล้าสมัย)

ลำดับขั้นที่ทำในคลิป

  1. รัน bootstrap script ใน repo เวิร์กชอป เพื่อสร้างข้อมูลตั้งต้น: agent, environment และ session เก่าๆ (เนื้อหาคีย์โน้ตวันที่หนึ่งกับเวิร์กชอปก่อนหน้า)
  2. ทดสอบกรณีฐาน: สร้าง session ชื่อ write test with no memory ผ่าน CLI แล้วส่งข้อความแรกให้ข้อมูลเกี่ยวกับ CMA talk (multi-agent orchestration, outcomes, memory) ดู status ใน console
  3. retest: สร้าง session ใหม่ ถามเรื่องเดิม agent ตอบไม่ได้เพราะไม่มี memory
  4. สร้าง memory store ผ่าน CLI ตั้งชื่อ (ตัวอย่างชื่อ CWC memory) ใส่คำอธิบาย แล้วดูใน console หมวด memory stores
  5. สร้าง session ที่แนบ memory store โดยส่ง memory store ID พร้อม prompt ชี้นำ และ access (อ่านเขียนเป็นค่าเริ่มต้น หรืออ่านอย่างเดียว) ส่งข้อมูลอีกรอบ agent จะอ่าน memory แล้วเขียนลงไฟล์ sessions.md
  6. สร้าง session ใหม่ที่ใช้ memory store เดิมแล้วถาม agent จะ grep หาคำอย่าง CMA ใน memory และตอบได้
  7. ตรวจ store ด้วย CLI (list memory files, ดูเวอร์ชัน) และดู file system viewer ใน console ที่แก้ไฟล์หรือเพิ่ม memory เองได้
  8. สร้าง dream job: ระบุโมเดล, input memory store, รายการ session ID, instructions เสริม แล้วได้ dream ID กลับมา
  9. ติดตามสถานะ (pending, running, completed) ใน console หรือ poll API ดู token count และเปิด session ของ dream เพื่อดู subagent
  10. ดู diff ของผลลัพธ์ใน console (ไฟล์ index, event logistics, ไฟล์เดิมที่จัดรูปใหม่)
  11. ดึง output memory store จาก dream resource ด้วย dream ID แล้วสร้าง session ใหม่แนบ store นั้น ถามว่าเข้าร่วม session ไหน มี link อะไร มี follow-up อะไร
  12. เมื่อพอใจ จะ retire memory store เก่าเพื่อคุมจำนวน store ในองค์กร (ไม่กระทบ session เก่า)

ตัวเลข / ข้อเท็จจริงที่ผู้พูดบอก

ตามที่ผู้พูดอ้างในคลิป ไม่ได้ยืนยันกับแหล่งอื่น

  • dream job รับโมเดล Claude Opus 4.7 หรือ Sonnet 4.6 (ตามที่ได้ยินจาก ASR)
  • จำนวน session ต่อ dream: ตัวอย่างประมาณ 10 หรือ 20 สูงสุดราว 100 ผู้พูดบอกว่ากำลังหาทางขยายเกินนี้
  • ผู้พูดคาดว่า cache hit rate ราว 95% ในการรัน dream ส่วนใหญ่ เพราะงานเป็น agentic
  • ผู้พูดบอกว่ากำลังสำรวจการลดราคา 50% คล้าย batch API โดยจัดตารางรันต่างเวลา (ยังเป็นแค่แนวคิด)
  • dream job ในเดโมใช้เวลาราว 1 นาที แต่บอกว่าของจริงอาจกินตั้งแต่ไม่กี่นาทีถึงหลายชั่วโมง
  • ผู้พูดบอกว่า access เริ่มต้นเป็นอ่านเขียน และเปลี่ยนเป็นอ่านอย่างเดียวได้

สิ่งที่นำไปทำต่อ

  • ให้ agent ที่ต้องรู้จักผู้ใช้หรือบริบทระยะยาวมี memory store แยกตามผู้ใช้หรือ workspace แล้วใช้ prompt ชี้นำว่าควรจดเรื่องไหน
  • ตั้ง access เป็นอ่านอย่างเดียวสำหรับ session ที่ไม่ควรแก้ memory
  • รัน dreaming เป็นรอบ เช่น รายวันกับ session ชุดหนึ่ง แล้วอ่าน diff ใน console ก่อนสลับไปใช้ output store
  • ใช้ instructions ของ dream job บอกโดเมนที่ต้องการรายละเอียดเฉพาะ หรือโครงสร้างไฟล์ที่อยากได้
  • มองเรื่อง token cost ของ dreaming ล่วงหน้า เพราะผู้พูดบอกว่าตั้งใจให้ใช้ token เยอะ และมีตัวเลือกลดต้นทุน เช่น เปลี่ยนโมเดลหรือกำหนดงบ token
