Claude Code ขั้นต่อไป: ปรับแต่ง agent ให้ scale ในงาน software engineering จริง

Beyond the basics with Claude Code

ผู้พูด: Daisy Holman (engineer ในทีม Claude Code (สะกดตาม Whisper), เคยเป็น chair ของ C++ committee)

เหมาะกับ: วิศวกรที่ใช้ Claude Code อยู่แล้วและต้องการวางระบบ customization ให้ทีม/monorepo ขนาดใหญ่ (รู้จัก MCP, skills, hooks เบื้องต้นมาก่อน)

ผู้พูดวางกรอบการปรับแต่ง Claude Code เป็น 3 อย่าง คือ access, knowledge, tooling แล้วไล่ดู MCP, skills, hooks, subagents ว่าตัวไหน scale ได้เมื่อ monorepo มี skill เป็นแสน เพราะ context window เป็นทรัพยากรจำกัดและ KV cache ทำให้เปลี่ยนของต้นๆ prompt แล้วแพง สรุปคือ hooks เป็น zero overhead จริง ส่วน MCP/skills/subagents ยังต้องจ่ายค่า description ใน system prompt ตลอด ช่วงท้ายเล่าวิธีทำงานแบบ parallel + async ด้วย worktrees, /loop, auto mode

Customizing Claude Code through access, knowledge and tooling, and judging MCP, skills, hooks and subagents by how they scale against a fixed context window and the KV cache. Hooks are the only true zero-overhead primitive; the talk ends with parallel/async workflows (worktrees, /loop, auto mode).

ประเด็นสำคัญ

  1. ถ้า Claude เข้าถึงสิ่งที่วิศวกรเข้าถึงไม่ได้ ก็ทำงานแทนไม่ได้ ผู้พูดชี้ว่างานส่วนใหญ่ไม่ได้อยู่ใน source code แต่อยู่ใน Slack, อีเมล, design doc, CI/CD, dashboard จึงต้องต่อ Claude เข้ากับสิ่งเหล่านี้ เคล็ดลับคือทำงานทั้งวันโดยไม่ออกจาก Claude Code แล้วจดทุกครั้งที่ต้อง alt-tab ไปหยิบข้อมูล นั่นคือสิ่งที่ Claude ยังขาด
  2. เรื่อง knowledge ผู้พูดบอกว่า fine-tuning ไม่เวิร์กกับ convention ของ codebase (เสี่ยง hallucination เพิ่ม, ไม่คุ้มเพราะ frontier model เปลี่ยนเร็ว) ทางที่เหลือคือ in-context learning ซึ่งก็คือไฟล์ข้อความ เช่น CLAUDE.md และ skills
  3. เรื่อง tooling เปรียบ post-tool-use hooks เป็น 'red squigglies' ของ agent คือ linter/LSP/เตือนว่าไฟล์นี้ generated ที่ชี้นำแต่ไม่บล็อก และ override ได้ แยกจากเครื่องมือที่ชดเชยความไม่ฉลาด (hard block) ซึ่งไม่ scale ตามความฉลาดของโมเดล
  4. context window เป็นเป้าที่นิ่ง (ราว 1M token ใน Opus 4.7 ตามที่พูด) เปรียบเหมือนรัน NPM บน Arduino ต้องใส่เฉพาะสิ่งสำคัญที่สุดในรูปเล็กที่สุด หลัก 'don't pay for what you don't use' และยังมีข้อจำกัด KV cache คือถ้าแก้ของต้น prompt ทุก token ที่ตามมาจะกลายเป็น uncached (แพงกว่าราว 10 เท่า) ต้องวางของ stable ไว้หน้า ของ volatile ไว้ท้าย
  5. MCP ออกแบบมาสำหรับ chatbot ที่ไม่มี shell: ถ้ามี CLI อยู่แล้ว การเขียน skill สอนใช้ CLI ง่ายกว่า MCP ยกเว้นส่งให้ลูกค้าไม่เทคนิค แต่ยังต้องใช้ MCP ของคนอื่นสำหรับ Slack/email และ tool schema ใน system prompt ทำให้ 20 servers x 15 tools กินเกือบทั้ง context ส่วน tool search ช่วยได้ระดับหนึ่งแต่ 'no free lunch'
  6. Skills คือ 'lazy system prompt': body จ่ายเมื่อใช้ แต่ description โหลดตลอด (ราว 300-400 token ถึงจะ trigger น่าเชื่อถือ) และยังไม่มี hierarchy หรือ lazy sub-skills ผู้พูดบอกว่าอาจมีประกาศเรื่องนี้ใน 2-3 สัปดาห์ ส่วน hooks เป็น zero overhead จริงเพราะรันนอก context ถ้าไม่ match ก็ไม่มีต้นทุน token
  7. Subagents ย้าย system prompt และการอ่านไฟล์ไปอยู่ context แยก แต่ description บรรทัดเดียวของแต่ละตัวยังอยู่ใน parent prompt ผู้พูดจึงไม่ยอมให้ plugin ใส่ CLAUDE.md แบบ unconditional (ดูถูกแต่แพงมาก) ถ้าจำเป็นให้คืนข้อความจาก session start hook เพื่อให้เห็นชัดว่าผู้ใช้จ่ายทุกครั้ง และมองว่า plugin คือ context engineering primitive ไม่ใช่ memory
  8. ทิศทางการทำงานคือ async + parallel ผู้พูดใช้ git worktrees อายุยาวหลายตัว แต่ละตัวมี agent เฉพาะ, /color และ rename เพื่อสลับ context, agents คุยกันผ่าน send message tool, /loop (cron tool) สำหรับ babysit PR, auto mode แทนการถาม permission (ผู้พูดบอกว่าแพงขึ้นราว 30-40% แต่ไม่แน่ใจตัวเลข), Cloud agents view และ Remote Control

ตัวเลข / ข้อเท็จจริงที่ผู้พูดบอก

ตามที่ผู้พูดอ้างในคลิป ไม่ได้ยืนยันกับแหล่งอื่น

  • context window ของ Opus 4.7 ราว 1 ล้าน token ตามที่ผู้พูดบอก (ผู้พูดว่า window ไม่ได้โตขึ้นเทียบกับปีก่อน)
  • uncached token ราคาแพงกว่า cached ประมาณ 10 เท่า ตามที่ผู้พูดอธิบายเรื่อง KV cache
  • MCP 20 servers x 15 tools ต่อตัว ผู้พูดบอกว่าส่วนใหญ่ของ context จะกลายเป็น tool definitions
  • description ของ skill ที่ trigger ได้น่าเชื่อถือมักยาวราว 300-400 token
  • ผู้พูดอ้างว่าบริษัทบางแห่งมี skill ใน monorepo เป็นหมื่นถึงแสนตัว และชนขีดจำกัด scaling
  • auto mode แพงขึ้นราว 30-40% (ผู้พูดบอกเองว่าไม่แน่ใจตัวเลข อาจน้อยกว่านี้แล้ว)
  • วิศวกรที่สร้าง Cloud agents view ผ่านงานราว 1,000 PR ในเดือนที่ผ่านมา ตามที่ผู้พูดเล่า

ประโยคเด่น (ต้นฉบับ)

“if Cloud can't do everything you can do, it can't do your job with you”

ถ้า Claude ทำทุกอย่างที่คุณทำไม่ได้ ก็ทำงานของคุณร่วมกับคุณไม่ได้

“The fastest way to make your agent better at your code base isn't a smarter model. It's a tighter feedback loop.”

ทางลัดที่ทำให้ agent เก่งขึ้นใน codebase ไม่ใช่โมเดลที่ฉลาดกว่า แต่เป็น feedback loop ที่แน่นกว่า

“You have to be very intentional about what you put into your context window.”

ต้องจงใจมากกับสิ่งที่ใส่เข้า context window

สิ่งที่นำไปทำต่อ

  • ลองทำงานทั้งวันโดยไม่ออกจาก Claude Code แล้วจดทุกครั้งที่ต้องสลับไปเครื่องมืออื่น จากนั้นต่อ Chat/CI/dashboard/doc เหล่านั้นให้ Claude
  • ใช้ post-tool-use hooks เป็น feedback แบบเตือน (linter, LSP, แจ้งว่าไฟล์ generated) แทน hard block ใช้สคริปต์ที่ทีมมีอยู่แล้ว
  • ถ้ามี CLI อยู่แล้ว เขียน skill สอนใช้ CLI ก่อนจะคิดห่อเป็น MCP server
  • เลือก abstraction ตามต้นทุนใน context: อะไรที่ต้องจ่ายตลอดเวลา (description, tool schema, CLAUDE.md ของ plugin) ให้ระวังเมื่อจำนวนโตเป็นพัน-แสน
  • ฝึกทำงาน parallel: worktree ต่อ agent, ตั้งชื่อ/สี session, /loop ดู PR, และลอง auto mode แทน dangerously-skip-permissions

  • ชื่อผู้พูด 'Daisy Holman' สะกดตามที่ Whisper ได้ยินจากการแนะนำตัว อาจเพี้ยน
  • transcript ไม่แยกผู้พูด ส่วนที่พูดเรื่องโครงสร้าง repo (Anthropic monorepos, Claude Code repos) ถอดมาไม่ชัดและมีประโยคสับสน จึงไม่ได้สรุป
  • ตัวเลข 30-40% ของ auto mode ผู้พูดบอกเองว่าไม่แน่ใจ
  • ข้ออ้างเรื่องงานวิจัยปลายปี 2025 ว่า fine-tuning ทำให้ hallucination มากขึ้น ผู้พูดไม่ได้ระบุที่มา ตรวจสอบไม่ได้
