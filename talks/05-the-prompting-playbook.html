#05 · โมเดล & Prompting · 33:49

Prompting playbook: ซ่อม prompt ที่มีอยู่ด้วย evals และสร้าง agent จากศูนย์

The prompting playbook

ผู้พูด: Margo van Laar (Applied AI engineer, Anthropic (London))

เหมาะกับ: เหมาะกับวิศวกรที่ดูแล prompt ใน production หรือกำลังย้ายโมเดล และเคยเขียน eval เบื้องต้นมาแล้ว

Margo van Laar พาดูสองสถานการณ์จริง คือซ่อม prompt เก่าที่พังหลังย้ายโมเดล (บอท support ของ Meridian Mobile) และสร้าง agent ใหม่ (จัดตารางพนักงาน) ข้อสรุปหลักคือเริ่มจาก eval แล้วแก้ failure mode ทีละข้อ เก็บกวาด prompt ให้มีโครงสร้าง ถอด patch เก่าที่ overfit ใส่ tool แทนการสั่งให้ทำดี และแยกงานเป็น prompt หลายตัวเมื่อทำ agent

Two walk-throughs, repairing a production prompt after a model migration (telco support bot) and building a scheduling agent from scratch. Start from evals, fix failure modes one at a time, clean up structure, remove stale patches, add tools, and split agent work into separate prompts.

ประเด็นสำคัญ

  1. เริ่มจาก eval suite ก่อนแตะ prompt เพราะต้องมีหลักฐานว่าการแก้ช่วยจริง ตัวอย่างมี 5 เทสต์ที่ครอบ 3 แบบ คือ control (ต้องผ่านเสมอ), edge case ที่เคยพลาด, และเคสที่โมเดลต้องส่งต่อมนุษย์หรือปฏิเสธ
  2. เก็บกวาดทั่วไปก่อน: เอาข้อมูลซ้ำที่ copy มาจากเว็บออก, เลิกบอกบอทว่าเป็นมนุษย์, แยก role/guidelines/policy/tone ด้วย XML tags ผลดีขึ้นทันที ตามหลัก ถ้าคนอ่านแยก guideline policy data ไม่ออก โมเดลก็น่าจะแยกไม่ออก
  3. ทำ output contract: กำหนดรูปแบบ output ด้วย XML tag และเพิ่ม stop sequence ที่ฝั่ง API ส่วน output ซับซ้อนให้ใช้ structured outputs
  4. เคส hotspot: โมเดลเลี่ยงตอบเพราะ prompt มีคำสั่งเก่า 'never give the wrong plan details' ที่เป็น patch จากโมเดลรุ่นก่อน ผู้พูดบอกว่าโมเดลใหม่ทำตามคำสั่งเก่งขึ้นจึง overfit ให้ปรับเป็นมุมที่สมดุล และเก็บเหตุผลของ patch ไว้ใน version control
  5. เคส proration: การสั่งว่า 'ต้องคำนวณให้ถูก' ไม่ได้เพิ่มความสามารถ แก้ด้วยการเพิ่ม tool คำนวณ (กำหนด schema, ใส่ใน API, เขียนฟังก์ชันจริง) โมเดลไม่ต้องคิดเลขในหัว
  6. เคส escalation: prompt บอกแต่ต้นทุนของการ escalate (ประมาณ $8) ทำให้โมเดล overfit ไปไม่ escalate ให้บอกทั้งสองด้านของ trade-off รวมต้นทุนเมื่อพลาด (refund และความเชื่อใจลูกค้า)
  7. สร้าง agent จัดตารางจากศูนย์: ตรวจด้วยฟังก์ชัน Python แทน LLM judge เพราะกฎตายตัว เทียบ Sonnet 4.6 (ล้มทุกเคส) กับ Opus 4.7 (ผิดน้อยลงแต่ยังไม่ผ่าน) กับ Opus 4.7 + adaptive thinking (ผ่านแต่ token และ latency เพิ่มราว 3 เท่า)
  8. ทางที่ดีกว่า: loop แบบ generate, evaluate, repair ที่แยกเป็น 3 prompt ผ่านทุกเคสด้วย token และ latency ต่ำกว่า Sonnet ที่ปรับ prompt และยังใส่ soft constraint ตอน runtime ได้ (เช่น คนสองคนไม่ควรเข้ากะเดียวกัน)

ลำดับขั้นที่ทำในคลิป

  1. ตั้ง eval suite 5 เคส (control, edge case, escalation/refusal) แล้วรัน baseline V0
  2. เก็บกวาด prompt: ลบเนื้อหาที่ copy จากเว็บ, แก้ role, แยกส่วนด้วย XML tags แล้วรัน eval ซ้ำ
  3. เพิ่ม output contract (รูปแบบ XML) และ stop sequence ที่ API call
  4. แก้เคส hotspot: เอาคำสั่ง 'never give the wrong plan details' ออก ให้ใช้ข้อมูลลูกค้าเป็น source of truth
  5. แก้เคส proration: เพิ่ม tool calculate proration (กำหนด schema, ลงทะเบียนใน API, implement ฟังก์ชัน) และสั่งใน prompt ให้ใช้ tool
  6. แก้เคส escalation: บอกทั้งต้นทุนของการ escalate และต้นทุนเมื่อตอบพลาด
  7. agent ใหม่ (จัดตาราง): เขียน baseline ด้วย Sonnet 4.6, ตรวจด้วยฟังก์ชัน Python, ลองเปลี่ยนเป็น Opus 4.7, ต่อด้วย adaptive thinking
  8. ลอง prompt ที่ดีขึ้นบน Sonnet 4.6 (บอกให้ตรวจงานก่อนตอบ) พบว่าชนเพดาน output token
  9. สร้าง loop generate, evaluate, repair แยก 3 prompt แล้วเทียบ token กับ latency

ตัวเลข / ข้อเท็จจริงที่ผู้พูดบอก

ตามที่ผู้พูดอ้างในคลิป ไม่ได้ยืนยันกับแหล่งอื่น

  • Eval ตัวอย่างมี 5 test cases (ของจริงจะมากกว่านี้) สำหรับบอท support ของบริษัทสมมติ Meridian Mobile
  • ต้นทุน escalate ไปหา care specialist ใน prompt เดิม: ประมาณ $8 ต่อเคส
  • เคส hotspot: ข้อมูลลูกค้า legacy plan มี 5 GB แต่ policy ปัจจุบันของแพ็กเกจ unlimited คือ 4 GB
  • งานจัดตาราง: พนักงาน 8 คน, รัน 5 trials ต่อการตั้งค่า, ตรวจด้วยฟังก์ชัน Python นับ violation
  • Opus 4.7 + adaptive thinking: ผู้พูดบอกว่า token เพิ่มราว 3 เท่าและ latency ราว 3 เท่า (ตัวอย่างหนึ่ง 100 วินาที)
  • โมเดลที่เทียบ: Sonnet 4.6 และ Opus 4.7

ประโยคเด่น (ต้นฉบับ)

“instructions don't add capability.”

คำสั่งไม่ได้เพิ่มความสามารถ

“if you're reading a prompt and you can't tell guidelines from policy from data, most likely the model isn't able to either.”

ถ้าอ่าน prompt แล้วแยก guideline, policy, data ไม่ออก โมเดลก็น่าจะแยกไม่ออกเหมือนกัน

“we need to remember to state both sides of the trade-offs”

ต้องบอกทั้งสองด้านของ trade-off

สิ่งที่นำไปทำต่อ

  • สร้าง eval ให้ครบ 3 แบบ (control, edge case, handoff) ก่อนแตะ prompt หรือย้ายโมเดล
  • ตรวจ prompt เก่าหา patch ที่เขียนไว้กันโมเดลรุ่นก่อน อาจ overfit กับโมเดลใหม่ และจดเหตุผลใน version control
  • ถ้าอยากให้งานแม่น (คำนวณ ฯลฯ) ให้ใส่ tool ไม่ใช่เพิ่มคำสั่งว่า 'critical'
  • เขียน trade-off ให้ครบสองด้าน แทนการใส่แต่ข้อห้ามหรือต้นทุนด้านเดียว
  • ถ้างานมีกฎตายตัว ลองแยก generate, evaluate, repair เป็น prompt สั้นๆ สามตัว แล้วเทียบกับการใช้โมเดลใหญ่ + thinking

ข้อควรระวังในสรุปนี้

  • ผู้พูดบอกว่าผลรันเป็น live demo มีความแปรปรวนระหว่างรอบ (เช่น เคส hotspot ถอยหลังชั่วคราวหลังเก็บกวาด) ผลที่เห็นไม่ใช่ benchmark
  • ตัวอย่างใช้ prompt ย่อส่วน 5 เทสต์ ผู้พูดบอกเองว่าของจริงจะยาวและซับซ้อนกว่า
  • ตัวเลข 3 เท่าของ token/latency เป็นค่าประมาณจากคำพูดของผู้พูด ไม่ได้เห็นตาราง
  • Transcript เป็น YouTube auto-caption จึงไม่ได้เห็นหน้าจอ ชื่อ tool/ฟังก์ชันที่ไม่ได้ออกเสียงไม่มีในสรุป
  • คำอธิบายคลิปบอกว่า 'ใช้หลัก prompting กับระบบ agentic' แต่เนื้อหาจริงเน้นการซ่อม prompt และเปรียบเทียบ 4 วิธีของ agent จัดตาราง
