สร้าง eval ให้ agent ทำสไลด์ แล้วไต่คุณภาพขึ้นทีละรอบ

Evals for taste: Hill-climbing a slide-generation agent

ผู้พูด: ไม่ได้ระบุชื่อใน transcript

เหมาะกับ: คนที่กำลังสร้าง agent และอยากรู้ว่า eval ควรวัดอะไร ออกแบบ grader อย่างไร ไม่ต้องมีพื้นมาก่อน

เวิร์กชอปพาสร้าง eval ให้ agent สร้างสไลด์ PowerPoint ตั้งแต่ code grader ง่ายๆ ไปจนถึง model judge แล้วใช้คะแนนที่ได้วนปรับ system prompt และเพิ่ม QA loop จนคุณภาพดีขึ้น ผู้พูดย้ำว่า eval ต้องเป็นของที่มีชีวิต ต้อง calibrate grader ต่อเนื่อง ไม่ใช่ตั้งครั้งเดียวแล้วเชื่อตลอด

A workshop on building evals for a slide-generation agent: code graders and LLM judges drive a prompt/QA-loop iteration cycle, with the warning that graders must be calibrated and kept alive.

ประเด็นสำคัญ

  1. Eval คือชุดทดสอบเชิงระบบที่วัดว่า AI ทำงานในโดเมนเฉพาะได้ดีแค่ไหน ช่วยแปลงความรู้สึกว่า 'วันนี้แย่ลงนะ' ให้เป็นสิ่งที่ลงมือแก้ได้ benchmark ทั่วไปอย่าง SWE-bench บอกเรื่องของคุณได้น้อย จึงควรสร้าง eval ของตัวเอง
  2. ไม่มี eval จะบินตาบอด ต้องรอลูกค้าบ่นแล้วค่อยตามแก้ แก้จุดหนึ่งอาจทำอีกจุดพัง และยืนยันไม่ได้ว่าดีขึ้นหรือถดถอย ส่วนมี eval แล้วต้องนิยาม 'ความสำเร็จ' ออกมาชัด ย้ายไปโมเดลใหม่ได้เร็วขึ้น และเห็นปัญหาก่อนปล่อย
  3. Grader มีสามแบบ code-based (เร็ว ถูก deterministic แต่เปราะและไม่มี nuance) model-based (rubric, pairwise comparison, multi-judge consensus ยืดหยุ่นแต่ non-deterministic และแพงกว่า) และ human grader (คุณภาพสูงสุดแต่แพงและช้าที่สุด ใช้ spot check/AB testing)
  4. ใน repo เวิร์กชอป agent นิยามด้วย agent.yaml (Managed Agents) code grader นับ emoji, จำนวนสไลด์, สไลด์ที่แน่นเกิน, ฟอนต์เล็ก, text-heavy ส่วน judge ให้คะแนน 0-5 ด้าน text, image, layout, color หลักคิดคือ grader ที่ไม่ให้ข้อมูลที่ลงมือแก้ได้ ไม่ควรอยู่ใน eval
  5. วงไต่คุณภาพ ดูผลสไลด์กับคะแนน แล้วแก้ system prompt ตามจุดที่พลาด (ขนาดตัวอักษร layout ห้าม emoji ห้ามเส้น accent บางๆ แบบ AI tell) แล้วรันใหม่ รอบหนึ่ง emoji count พุ่งเป็น 20 ทั้งที่ผู้พูดไม่เห็นในสไลด์ แปลว่า grader ยังนิยามไม่ดี จึงต้องมนุษย์ตรวจควบคู่
  6. เพิ่มข้อกำหนดว่าทุกสไลด์ต้องมีไดอะแกรมหรือกราฟเป็นภาพจริง แล้วเพิ่ม QA loop ที่สั่ง agent ให้ 'assume there are problems' ทำ QA เหมือนล่าบั๊ก แปลงสไลด์เป็นภาพ ตรวจทุกหน้า แก้ render ใหม่ อย่างน้อยหนึ่งรอบ คะแนน judge ขยับไปราว 4.2-4.4
  7. ลองสลับเป็น Opus 4.7 กับ prompt เริ่มต้นสั้นๆ ผลดีกว่า Sonnet อย่างเห็นได้ชัด แทบไม่ใช้ emoji แต่คะแนน judge สูงลิ่วทั้งที่บางรอบไม่มีภาพเลย ผู้พูดชี้ว่า rubric ไม่มีจุดยึด (ไม่มีตัวอย่างว่า 0 หรือ 5 หน้าตาเป็นอย่างไร) จึงควรเขียน anchor ตัวอย่างและบังคับให้ judge ให้เหตุผลก่อนแล้วค่อยให้คะแนน เพราะ LLM จะหาเหตุผลมาปกป้องตัวเลขที่พูดไปก่อน

ลำดับขั้นที่ทำในคลิป

  1. นิยาม agent ใน agent.yaml (Managed Agents) พร้อม system prompt สั้นๆ ให้สร้างไฟล์ PowerPoint ด้วย Python PPTX ใน shell
  2. รัน agent สร้างสไลด์ 5 หน้า แล้วดูผลจริงเพื่อหา failure mode (ข้อความทับกัน สีแปลก ฟอนต์เล็ก emoji)
  3. เขียน code grader (emoji count, slide count, cluttered, small font, text-heavy, slides with image) และ judge (color, image, layout, text, title-body coherence ให้คะแนน 0-5)
  4. รัน script ให้คะแนนอัตโนมัติ อ่าน score.json แล้วแก้ system prompt ตามจุดที่พลาด (typography, layout/density, ห้าม AI tells)
  5. เพิ่มข้อกำหนดทุกสไลด์ต้องมีไดอะแกรม/กราฟเป็นภาพ แล้วรันซ้ำและเทียบคะแนน
  6. เพิ่ม QA loop แบบ adversarial: แปลงสไลด์เป็นภาพ ตรวจทุกหน้า แก้ render ซ้ำ อย่างน้อยหนึ่งรอบ fix-and-verify
  7. สลับเป็น Opus 4.7 ด้วย prompt พื้นฐาน เทียบผล แล้วย้อนไปปรับ rubric ของ judge ให้มี anchor และให้เหตุผลก่อนให้คะแนน

ประโยคเด่น (ต้นฉบับ)

“systematic tests that measure how well an AI system performs on a specific domain or use case”

eval คือชุดทดสอบเชิงระบบที่วัดผลงานของ AI ในโดเมนหรือ use case เฉพาะ

“It's not because you have set up your evals once that they are now like the ground truth”

ตั้ง eval ครั้งเดียวไม่ได้แปลว่ามันเป็นความจริงสูงสุดตลอดไป

“Approach QA as a bug hunt, not a confirmation step.”

ให้ทำ QA แบบล่าบั๊ก ไม่ใช่ขั้นตอนยืนยันว่าดีแล้ว

สิ่งที่นำไปทำต่อ

  • สร้าง eval ของ use case ตัวเองก่อนเชื่อ benchmark ทั่วไป และถามทุก grader ว่าให้ข้อมูลที่ลงมือแก้ได้ไหม ถ้าไม่ ตัดทิ้ง
  • ใช้ code grader กับของที่นับได้แน่ๆ ใช้ model judge กับของที่ต้องใช้วิจารณญาณ และเขียน rubric พร้อมตัวอย่าง anchor ว่าคะแนนต่ำสุดสูงสุดหน้าตาอย่างไร
  • สั่ง judge ให้เขียนข้อดีข้อเสียและเหตุผลก่อน ค่อยให้คะแนนท้ายสุด กันไม่ให้ LLM แต่งเหตุผลมาปกป้องตัวเลขที่เลือกไว้แล้ว
  • เพิ่ม QA agent หรือ QA loop แบบสันนิษฐานว่ามีปัญหา แล้วป้อนผลกลับไปให้ agent ผู้สร้างจนทั้งสองฝั่งพอใจ
  • อ่านผลจริงด้วยตาควบคู่คะแนนเสมอ เมื่อคะแนนกับสิ่งที่เห็นขัดกัน ให้แก้ grader ไม่ใช่เชื่อตัวเลข และทดลองสลับโมเดลที่เก่งขึ้นโดยใช้ eval ชุดเดิมวัด

ข้อควรระวังในสรุปนี้

  • ไม่มีการแนะนำชื่อผู้พูดใน transcript จึงใส่ speakers เป็นว่าง
  • ตัวเลขคะแนนและชื่อรุ่นโมเดลมาจาก ASR ผู้พูดพูด 'Sonnet 4 7' แล้วแก้เป็น '4 6' จึงบันทึกเป็นไม่ชัดเจน
  • ผู้พูดอ้างว่าทำชุดสไลด์ผลลัพธ์ล่วงหน้าไว้ ตัวเลขทั้งหมดมาจากการเดโมในห้อง ไม่ใช่ผลวัดซ้ำที่ตรวจสอบได้
  • ผู้พูดบอกว่า 'Tower Bench' ซึ่งน่าจะเป็นชื่อ benchmark ที่ ASR เพี้ยน ไม่ได้ใส่เป็นข้อเท็จจริง
