ทำให้ agent น่าเชื่อถือด้วยภาษา DSL ของตัวเอง (กรณี Elicit กับ AshPL)

Making agentic workflows trustworthy and verifiable with a custom DSL

ผู้พูด: James Brady (Elicit (ใน transcript ถูกเขียนว่า 'Alissa'/'illicit' จาก ASR))

เหมาะกับ: คนออกแบบ agent ที่ต้องการความน่าเชื่อถือสูง (งานวิจัย การตัดสินใจเสี่ยงสูง) และสนใจสถาปัตยกรรมเบื้องหลัง ควรเข้าใจ interpreter และ event sourcing คร่าวๆ

James Brady เล่าว่า Elicit ให้ research agent เขียนแผนงานเป็น AshPL ซึ่งเป็น DSL ย่อยของ Python ที่ Turing incomplete แล้วให้ตัว interpreter รันแผนนั้นจริง ทำให้กระบวนการตรวจสอบได้ ต่อยอดได้โดยไม่เพี้ยน และทำตามแผนจริง ข้อสรุปคือไม่ได้ชวนให้ทุกคนใช้ DSL แต่ให้ใส่ใจ mechanism ว่าคำตอบเกิดขึ้นอย่างไร

Elicit's research agent writes plans in AshPL, a Turing-incomplete Python subset that an interpreter actually executes, making the process legible, iterable without drift, and faithfully followed. The pitch: care about the mechanism.

ประเด็นสำคัญ

  1. คำถามตั้งต้น ถ้าสองระบบให้ผลลัพธ์ตัวอักษรเหมือนกัน เราเชื่อมันเท่ากันไหม คำตอบคือขึ้นกับกระบวนการข้างใน mechanism สำคัญไม่แพ้ผลลัพธ์ และไม่มี mechanism เดียวที่ถูกสำหรับทุกกรณี มี trade-off ระหว่างความเร็วกับความเข้มงวด
  2. Elicit วางตัวเรื่องความน่าเชื่อถือสูง คุณภาพสูง และ data provenance จึงตั้งสามข้อ (desiderata) คือ process ต้อง legible ทั้งต่อผู้ใช้และ agent อื่น, การ iterate ต้องไม่เพี้ยนจากเจตนาเดิม (fidelity), และระบบต้องทำตามแผนจริง (followed faithfully)
  3. AshPL เป็น DSL ที่ Turing incomplete ไม่มี loop ไม่มี recursion ไม่มี mutation เป็น purely functional แบบ reactive และเป็น subset แบบมีหลักการของ Python มี type และมี primitive เฉพาะโดเมน เช่น ดึงงานวิจัยหรือ clinical trial เหตุผลที่เลือกพื้นฐาน Python คือโมเดลมีตัวอย่างเยอะอยู่แล้ว ไม่ต้องเรียนไวยากรณ์ใหม่
  4. แกนของระบบคือ loop เขียนแล้วตีความแล้วเขียนใหม่ curator เป็นตัวเขียน AshPL (ใช้ Agent SDK และเคยลอง Pi) Python service parse ตรวจ syntax และ type check ถ้า error ส่งกลับไปแก้ทันทีโดยแทบไม่เสียต้นทุน แล้ว interpret ด้วยโค้ด Python ธรรมดา
  5. สถาปัตยกรรมประกอบด้วย UI, event log แบบ append-only (event sourcing), Python service เป็น message broker, sandbox, wrapper ที่สลับ harness/โมเดลได้ และ gateway ที่เก็บ API key ไว้ เพื่อกัน user input หลอก curator ให้พิมพ์ env ออกมา
  6. ทุกรอบ interpret โปรแกรมทั้งก้อนใหม่ตั้งแต่ต้น แต่เร็วเพราะ content-addressable store ทำ memoization (hash expression ถ้าเคยคำนวณแล้วก็ใช้ซ้ำ) ซึ่งเป็นไปได้เพราะภาษาเป็น pure ผู้พูดว่าการ interpret ทั้งโปรแกรมช่วยให้มั่นใจเรื่อง cohesion และกัน drift
  7. เดโมคือ research landscape ของบริษัทที่ลงทุนด้าน foundation model สำหรับชีววิทยา ได้ตารางเป็น artifact ที่คลิกดูโค้ด AshPL ที่สร้างตารางนั้นได้ มี visualization ที่ derive จากโค้ดเดียวกัน และต่อยอดด้วย join กับตาราง oversight bodies โดยโปรแกรมยาวขึ้นแต่ส่วนต้นเหมือนเดิมและ cache ได้
  8. งานส่วนใหญ่ไม่ใช่ตัว DSL แต่เป็นวิศวกรรมซอฟต์แวร์ทั่วไป เช่น wrapper, interrupt handling, rehydrate session, credential isolation, จัดการ message ของโมเดล, event sourcing และทีม eval โดยเฉพาะที่ยากเพราะระบบเขียนโปรแกรมแล้วรันสดๆ

ประโยคเด่น (ต้นฉบับ)

“my pitch is that you should care a lot about the mechanism”

ข้อเสนอของผมคือให้ใส่ใจกับ mechanism ให้มาก

“the Ash PL is not just a representation of a plan. It is literally the plan which is executable”

AshPL ไม่ใช่แค่ตัวแทนของแผน แต่คือแผนที่รันได้จริง

“firstly it is Turing incomplete. It's relatively simple. There's no loops.”

ข้อแรกคือมัน Turing incomplete ค่อนข้างเรียบง่าย ไม่มี loop

สิ่งที่นำไปทำต่อ

  • ถามตัวเองก่อนว่าผลิตภัณฑ์ต้องการ legibility, fidelity ตอนต่อยอด และ faithfulness ต่อแผนแค่ไหน ถ้าสูงมาก ให้ทำแผนเป็นของที่รันได้ ไม่ใช่แค่ข้อความ
  • ถ้าจะทำ DSL ให้ย่อยจากภาษาที่โมเดลรู้จักดีอยู่แล้วเพื่อลดการสอนไวยากรณ์ และตัดฟีเจอร์ที่ไม่จำเป็น เช่น loop, recursion, mutation
  • ใช้ type check กับ parse เป็นด่านราคาถูกก่อนรัน แล้วส่ง error กลับให้ agent แก้ ก่อนเสียโทเค็นกับขั้นตอนแพง
  • ถ้ารันทั้งโปรแกรมใหม่ทุกรอบ ให้ทำ memoization ผ่าน content-addressed store เพื่อไม่ให้ซ้ำงาน
  • แยก credential ออกจาก agent ผ่าน gateway และลงทุนกับ eval ตั้งแต่ต้น เพราะ eval ของระบบที่เขียนโปรแกรมสดๆ ยากแต่จำเป็น
