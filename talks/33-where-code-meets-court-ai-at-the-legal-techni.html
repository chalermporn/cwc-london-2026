งานสิทธิบัตรไม่เหมาะกับการ delegate ให้ agent: ออกแบบ AI แบบ collaboration

Where code meets court: AI at the legal-technical frontier

ผู้พูด: Olly Cobb (Founding AI engineer, Solve Intelligence)

เหมาะกับ: คนที่สร้างผลิตภัณฑ์ AI ให้งานเฉพาะทางที่ตัดสินผิดแล้วแพง (กฎหมาย การเงิน) ไม่ต้องมีพื้นสิทธิบัตรมาก่อน ผู้พูดอธิบายให้ในคลิป

Olly Cobb จาก Solve Intelligence เล่าว่างานร่างสิทธิบัตรต่างจากงานเขียนโค้ด เพราะตรวจความถูกต้องไม่ได้ทันทีและการตัดสินใจแต่ละข้อผูกกันหมด โมเดล delegate ให้ agent วิ่งยาวเลยไม่เวิร์ก ทางที่เขาเสนอคือ collaboration โดยยึดสามหลัก ได้แก่ citations เป็นพลเมืองชั้นหนึ่ง, ใช้ general purpose agent ตัวเดียวรับ workflow เฉพาะทาง และ parallelize alignment แล้วค่อย sequence execution

Patent drafting resists the delegate-to-an-agent model because outputs can't be validated and decisions are entangled; Solve Intelligence builds for collaboration using first-class citations, one general-purpose agent behind specific workflows, and parallel alignment before sequential execution.

ประเด็นสำคัญ

  1. ผู้พูดวางกรอบว่า software dev ได้ประโยชน์จาก AI ด้านการให้เหตุผลเชิงเทคนิค ส่วนงานกฎหมายได้ประโยชน์ด้านการกวาดเอกสารเป็นพันเป็นล้าน patent law อยู่ตรงกลางที่ต้องการทั้งสองอย่าง
  2. เล่าพื้นฐานสิทธิบัตร เป็นสัญญาสังคมระหว่างผู้ประดิษฐ์กับรัฐ เปิดเผยการทำงานของสิ่งประดิษฐ์ แลกกับสิทธิผูกขาด 20 ปี ต้องผ่านเกณฑ์ novel, non-obvious, useful และ sufficiently disclosed โดย claims เป็นหัวใจที่กำหนดขอบเขตการคุ้มครอง
  3. ผู้พูดอธิบาย lifecycle ผ่าน prosecution (office action, การโต้แย้งหรือ amend claims, file history) ไปจนถึง enforcement และ litigation ข้อสรุปคือการตัดสินใจตอนร่างส่งผลอีกหลายปีข้างหน้า
  4. เหตุผลหลักที่ delegation ไม่เวิร์ก ข้อแรก validate output ไม่ได้ (รัน patent ไม่ได้ ความถูกต้องขึ้นกับเหตุการณ์ในอนาคต) ข้อสอง การตัดสินใจ entangled กัน (แก้ claim 1 ย้อนไปกระทบ claims อื่น, spec, drawings) สองข้อนี้รวมกันจึงพัง
  5. เหตุผลรองคือสิ่งประดิษฐ์เป็น out of distribution สำหรับโมเดล, hallucination ตรวจยากและแพงกว่า, ข้อมูลไม่ใช่ข้อความล้วน (line drawings, โครงสร้างเคมี, sequence ชีวภาพ) ซึ่งการเลือกวิธี represent มีผลต่อการ reason ส่วนโครงสร้างเอกสารที่สม่ำเสมอเป็นข้อที่ตัดสินได้สองทาง
  6. ทางเลือกคือ collaboration: AI ยกประเด็นที่ต้องตัดสินใจขึ้นมาให้ทนายในจังหวะที่ต้องตัดสิน พร้อม trade-off แล้วลงมือทำตามที่ตัดสินแล้ว ผู้พูดบอกว่าไม่ใช่ขาวดำ แต่ผลผลิตหน้าตาต่างกันทั้ง UI/UX และชั้น AI
  7. หลักที่ 1 citations เป็น first-class citizen ข้อมูลทุกอย่างที่ LLM เห็นต้องอยู่ในรูปที่อ้างอิงได้ และ LLM คุยกับผู้ใช้หรือคุยกันเองต้องระบุที่มา ซึ่งมักต้องออกแบบ pattern ของ tool calling, subagents, compaction เอง
  8. หลักที่ 2 ใช้ general purpose agent ตัวเดียวรับ workflow เฉพาะ ผู้ใช้กำหนดผ่าน interface (เช่น ร่าง claims ตามที่ตั้งค่าไว้) แล้วแปลงเป็นคำสั่งส่งเข้า agent ตัวเดิม อาจเสริม tool หรือ subagent ผู้ใช้จึงได้ทั้ง interface และ reasoning กับ citations ที่คุ้นเคย หลักที่ 3 parallelize alignment, sequence execution: ให้ sub-reviews ตามเกณฑ์รันขนาน สร้าง comments ให้ทนายตอบหรือ dismiss ก่อน แล้วค่อยให้ agent แก้เอกสารตามที่ตกลง

ตัวเลข / ข้อเท็จจริงที่ผู้พูดบอก

ตามที่ผู้พูดอ้างในคลิป ไม่ได้ยืนยันกับแหล่งอื่น

  • สิทธิบัตรให้สิทธิผูกขาด 20 ปีต่อผู้ประดิษฐ์ ตามที่ผู้พูดอธิบาย
  • เกณฑ์ขอรับสิทธิบัตร 4 ข้อตามที่ผู้พูดบอก: novel, non-obvious, useful, sufficiently disclosed
  • ในเดโม review รันแยก sub-review ขนานกัน 4 เกณฑ์ที่ Solve แนะนำ ผู้พูดบอกว่าใช้งานจริงอาจมีราว 30 เกณฑ์หรือมากกว่า

ประโยคเด่น (ต้นฉบับ)

“you can't run a patent, unfortunately, and its correctness is really a function of events that haven't happened yet”

รัน patent ไม่ได้ ความถูกต้องขึ้นกับเหตุการณ์ที่ยังไม่เกิด

“what we need here is something more akin to a model of collaboration rather than merely delegation”

ที่ต้องการคือโมเดลแบบ collaboration มากกว่า delegation ล้วนๆ

“citations are actually a massive pain”

citations เป็นเรื่องยุ่งยากมากจริงๆ

สิ่งที่นำไปทำต่อ

  • ก่อนทำ agent ให้โดเมนไหน ลองถามสองข้อก่อน ตรวจผลลัพธ์อัตโนมัติได้ไหม และการตัดสินใจแยกจากกันได้ไหม ถ้าไม่ใช่ทั้งคู่ delegation ล้วนไม่น่าเวิร์ก
  • ออกแบบ citations ตั้งแต่ต้นให้ข้อมูลที่ป้อน LLM อ้างอิงได้ และเช็กว่ายังอยู่รอดผ่าน subagent กับ compaction
  • ทำ workflow เฉพาะทางเป็น interface ที่แปลงเป็นคำสั่งเข้า general purpose agent ตัวเดียว แทนการแยกระบบ
  • เจอบทตรวจสอบหลายเกณฑ์ ให้ออก comments ขนานก่อน รอมนุษย์ตกลง แล้วค่อยรันแก้แบบเรียงลำดับ กันข้อเสนอแก้ที่ชนกัน
  • ถ้าโดเมนมีข้อมูลที่ไม่ใช่ข้อความ ลงแรงกับวิธี represent ข้อมูลให้โมเดลอ่าน เพราะผู้พูดบอกว่าเป็นจุดที่ application layer เพิ่มคุณค่าได้

ข้อควรระวังในสรุปนี้

  • transcript มาจาก Whisper large-v3 ที่ถอดเอง (ไม่ใช่คำบรรยายต้นฉบับ) ชื่อเฉพาะอาจเพี้ยน เช่น 'co-work' ในต้นฉบับน่าจะหมายถึง Cowork
  • ช่วงอธิบายหลักที่ 1 ถึงต้นหลักที่ 2 ในไฟล์มีประโยคซ้ำและขาดหาย (ประโยคท้ายหลักที่ 1 ซ้ำกันเอง และเนื้อหาต่อไปโดดมาที่กลางหลักที่ 2) จึงสรุปหลักที่ 2 จากที่เดโมอธิบายเพิ่ม
  • ประโยคเรื่อง 'the patent is not a specific syntax' ในต้นฉบับขาดความหมาย ไม่ได้ใช้ในสรุป
  • ทุกข้ออ้างเรื่องข้อดีของแนวทางเป็นมุมมองของผู้พูดในฐานะผู้ทำผลิตภัณฑ์ ยังไม่มีตัวเลขวัดผลในคลิป
