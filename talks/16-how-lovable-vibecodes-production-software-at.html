Lovable ทำให้แพลตฟอร์ม vibe coding ซ่อมตัวเองได้ยังไง (Lovable Overflow + vent tool)

How Lovable vibecodes production software at scale

ผู้พูด: Fabian Hedin (Cofounder และ CTO ของ Lovable (ตามคำอธิบายคลิป; ใน transcript ผู้พูดไม่ได้พูดชื่อตัวเอง))

เหมาะกับ: คนที่สร้างแพลตฟอร์ม agent ให้ผู้ใช้ทั่วไป และอยากรู้วิธีเอา failure จริงมาวนปรับปรุงระบบ (ไม่ต้องรู้ Lovable มาก่อน)

CTO ของ Lovable เล่าว่า ผู้ใช้ที่ไม่ใช่นักพัฒนาพอติดขัดแล้วหลุดจากแพลตฟอร์มง่ายมาก ทีมเลยสร้างระบบให้แพลตฟอร์มซ่อมตัวเอง 2 ชั้น ชั้นแรกคือ Lovable Overflow คลังปัญหาและวิธีแก้ที่ฉีดเข้า context ของ agent ก่อนผู้ใช้ติด ชั้นที่สองคือ vent tool ที่ให้ agent ส่งความหงุดหงิดกลับมา แล้ว agent อีกตัวเปิด PR ให้วิศวกรรีวิว ผู้พูดอ้างว่าลดอัตรา stuck ได้ 5% และ merge fix เข้า production ราว 10 รายการต่อวัน

Lovable's CTO describes two self-healing systems for a consumer vibe-coding platform: Lovable Overflow (a curated problem/solution corpus injected into the agent's context) and a vent tool through which the agent reports platform friction and agents open PRs for engineers to review.

ประเด็นสำคัญ

  1. Lovable เริ่มจากแนวคิดทำซอฟต์แวร์ให้คนที่เขียนโค้ดไม่เป็น (ผู้พูดเรียกว่า 99%) UI เป็นแชตซ้ายกับ preview ขวา ซึ่งแทบไม่เปลี่ยนมาตลอด แต่ความสามารถของโมเดลข้างหลังเปลี่ยนไปมาก ผู้พูดบอกว่าโมเดลเริ่มเอื้อให้ abstraction แบบนี้ใช้ได้จริงเมื่อราวปีครึ่งก่อน
  2. หลักการสองข้อของทีม คือทำ production grade software ไม่หยุดที่ prototype และทำให้ผู้ใช้ที่ไม่ใช่เทคนิคใช้ได้ ซึ่งยากกว่า เพราะไม่มีผู้เชี่ยวชาญอยู่ใน loop คอยช่วย
  3. ผู้พูดเทียบกับคำกล่าวเก่าว่า 10% สุดท้ายกินเวลา 90% แล้วบอกว่าใน vibe coding ก็เป็นแบบเดียวกัน ได้เวอร์ชันแรกเร็วแต่การทำให้จบกินเวลานาน ถ้าผู้ใช้ติดแล้วแก้เองไม่ได้ ถือเป็นประสบการณ์ที่แย่ที่สุด เป้าหมายทางเทคนิคคือให้ทุกแอปที่สร้างบนแพลตฟอร์มช่วยให้แอปถัดไปดีขึ้น
  4. นิยามคำว่า stuck มี metric ภายในชื่อ is_stuck เป็นจริงเมื่อผู้ใช้ขอสิ่งเดิมซ้ำ 3 ครั้งติด บ่นเรื่องผลงาน หรือขอแล้วหายไปเลย ใช้ classification model ขนาดเล็กตัดสิน แล้วแบ่งเป็น 3 กลุ่ม คือแก้ได้ด้วยการ prompt ใหม่ / เรื่องง่ายที่แพลตฟอร์มยังไม่รองรับ / ต้องลงทุนใหญ่ เช่น server side rendering เพื่อ SEO ที่เพิ่งปล่อยเมื่อสัปดาห์ก่อน
  5. Lovable Overflow ตั้งชื่อตาม Stack Overflow เป็นคลังคำอธิบายปัญหาพร้อมวิธีแก้ พอผู้ใช้พิมพ์ปัญหา เช่น scroll กระตุก ระบบจะค้นคลังโดยดู tech stack กับเวอร์ชัน package แล้วให้ lightweight model ปรับความรู้ให้เข้ากับสถานการณ์ก่อนฉีดเข้า main agent ไม่ใช่ dump ดิบๆ
  6. ความรู้ในคลังมีอายุ ระบบเลยเก็บ success ratio ต่อไฟล์ความรู้ และตัดทิ้งเมื่อล้าสมัย พร้อมเติมความรู้ใหม่ ผู้พูดบอกว่าการจูนจังหวะ deprecate กับเพิ่มความรู้เป็นส่วนสำคัญที่สุดของการทำให้ระบบนี้ใช้ได้ และเคยลองทำแล้วล้มเหลวเพราะยังไม่จูนสัญญาณให้ดี
  7. vent tool คือ tool ของ agent ชื่อ vent --send_feedback ใช้ได้ครั้งเดียวต่อข้อความผู้ใช้ เมื่อเอกสาร tool หรือพฤติกรรมแพลตฟอร์มทำให้งานช้าลงหรือแย่ลง ข้อความไปลง Slack แล้ว agent อีกตัวคัด dedupe สืบสวน และเปิด PR ให้วิศวกรรีวิว ผู้พูดบอกว่าราว 50% ของ PR มีเหตุผลถูกต้อง
  8. ตัวอย่างที่ผู้พูดเล่า คือ tool copy ไฟล์พังกับชื่อไฟล์ที่มีอักขระพิเศษ แล้วมี PR merged ใน production ภายใน 10 นาที, agent บ่นเรื่อง type ของ Framer Motion, ช่วง production incident ยอด vent พุ่งจนกลายเป็นสัญญาณแรกของ incident หลายครั้ง และ agent ที่ vent ซ้ำ 43 ครั้งก็เสนอ dedupe safeguard เองจนถูก merge
  9. บทเรียนที่ผู้พูดสรุป คือการเรียนรู้จาก failure ผูกกับโมเดลที่ใช้ เมื่อมีโมเดลใหม่ต้องจูนหรือตัดความรู้ที่โมเดลรู้อยู่แล้วออก ความรู้มี half-life และระบบต้องจูนตลอดด้วยสัญญาณจากข้อมูลจริงของแพลตฟอร์ม

ตัวเลข / ข้อเท็จจริงที่ผู้พูดบอก

ตามที่ผู้พูดอ้างในคลิป ไม่ได้ยืนยันกับแหล่งอื่น

  • ผู้พูดบอกว่าแพลตฟอร์มมี 50 ล้านโปรเจกต์ และเว็บที่สร้างบน Lovable มี 600 ล้าน monthly visits (คำอธิบายคลิปเขียน 600M+ monthly sessions)
  • GPT-Engineer repo ของผู้ร่วมก่อตั้ง Anton เกิดเมื่อราว 35 เดือนก่อน และผู้พูดบอกว่าเป็น repo ที่ได้ stars เร็วที่สุดบน GitHub ในตอนนั้น
  • is_stuck เป็นจริงเมื่อขอสิ่งเดิมซ้ำ 3 ครั้งติด
  • ผลของ Lovable Overflow เวอร์ชันแรกเทียบกับไม่มี: อัตรา stuck ลดลง 5% และ publish rate เพิ่มขึ้น 2% ผู้พูดบอกว่า 5% นี้อยู่ในระดับเดียวกับที่ metric ขยับเมื่อมีโมเดลรุ่นใหม่
  • vent tool: merge fix เข้า production ราว 10 รายการต่อวัน และ PR ราว 50% ที่ agent เสนอมีเหตุผลถูกต้อง
  • ตัวอย่างบั๊ก tool copy ไฟล์ มี PR merged ใน production ภายใน 10 นาทีหลังได้รับ vent
  • agent เรียก vent 43 ครั้งในกรณีที่ spam Slack ก่อนเสนอ dedupe safeguard เอง
  • ผู้พูดบอกว่ามีแอปใหม่ราว 200,000 ต่อวัน และข้อความหลายล้านต่อวัน ใช้เป็นสัญญาณจูนระบบ

ประโยคเด่น (ต้นฉบับ)

“every app that is built on the platform should help improve the next”

ทุกแอปที่สร้างบนแพลตฟอร์มควรช่วยให้แอปถัดไปดีขึ้น

“if you give the agent a tool to tell you when it's feeling frustration, that's another way to do it”

ถ้าให้ agent มี tool บอกเราตอนมันหงุดหงิด นั่นก็เป็นอีกทางหนึ่ง

“knowledge has a half-life”

ความรู้มีครึ่งชีวิต

สิ่งที่นำไปทำต่อ

  • ถ้าทำแพลตฟอร์ม agent ให้ผู้ใช้ทั่วไป นิยาม metric ว่าผู้ใช้ติดขัดตอนไหน (ขอซ้ำ บ่น หายไป) ก่อน แล้วค่อยออกแบบระบบแก้
  • ทำคลังความรู้ปัญหา/วิธีแก้ แล้วฉีดเข้า context เฉพาะตอนเกี่ยวข้อง พร้อมวัด success ratio ต่อรายการเพื่อตัดความรู้ที่ล้าสมัย
  • ลองให้ agent มี tool ส่ง feedback เรื่อง tool/doc/platform ที่ใช้ไม่ได้ แล้วต่อเข้า Slack กับ agent คัดกรองที่เปิด PR ให้คนรีวิว
  • ใช้ปริมาณ vent เป็นสัญญาณเสริมตอนสืบ incident ควบคู่กับ monitoring ปกติ
  • เมื่อเปลี่ยนโมเดล ทบทวนคลังความรู้ด้วย บางอย่างต้องจูนใหม่ บางอย่างโมเดลรู้อยู่แล้วจนไม่ต้องมี

ข้อควรระวังในสรุปนี้

  • transcript มาจาก Whisper large-v3 ที่ถอดเอง ไม่ใช่ caption ทางการ ชื่อเฉพาะและตัวเลขอาจเพี้ยน
  • ชื่อ Fabian Hedin มาจากคำอธิบายคลิป ผู้พูดไม่ได้พูดชื่อตัวเองใน transcript
  • ประโยค 50,000 million apps now ฟังเพี้ยนชัดเจน (ช่วงต้นผู้พูดพูดว่า 50 million projects) จึงใช้ 50 ล้านโปรเจกต์ตามช่วงต้น; stack rate ที่ได้ยินน่าจะเป็น stuck rate
  • ผลลดอัตรา stuck 5% และ publish rate +2% เป็นตัวเลขที่ผู้พูดรายงานเอง ไม่มีหลักฐานอิสระ และเป็นของเวอร์ชันแรกของระบบ
  • ผู้พูดเสนอไอเดียให้ agent contribute เข้า open source library แต่บอกว่ายังไม่อนุญาตและไม่แน่ใจว่าทำอะไรไปแล้ว ไม่ใช่ฟีเจอร์ที่ใช้อยู่
