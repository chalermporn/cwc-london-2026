ปุ่ม thinking และ effort: ให้ Claude ใช้ compute ตอนรันมากน้อยแค่ไหน

The thinking lever

ผู้พูด: Alexander Briken (applied AI research team, Anthropic (สะกดนามสกุลตาม ASR))

เหมาะกับ: นักพัฒนาที่ใช้ Claude API/Claude Code และสงสัยว่าควรตั้ง effort กับ thinking ระดับไหน ควรรู้จักโมเดล Haiku/Sonnet/Opus ในระดับพื้นฐาน

Alexander อธิบาย test-time compute ว่าเมื่อ Claude ใช้ token คิดมากขึ้นคุณภาพก็ดีขึ้น โดยมี 3 ทางใช้ compute คือ thinking, tool calling และ text ควบคุมได้ด้วย effort กับ budget เขาย้ำว่า adaptive thinking ไม่ใช่ model router และการปิด thinking ไม่ใช่การลด effort แต่คือการถอด capability ออก คำแนะนำคือเปิด thinking ไว้ ทดสอบด้วย eval และเมื่อไม่แน่ใจเริ่มที่ extra high

More test-time compute improves results; control it with effort levels and budgets, keep thinking enabled (adaptive thinking), evaluate per task, and default to extra high when unsure.

ประเด็นสำคัญ

  1. test-time compute คือการใช้ token ตอน inference เพื่อให้โมเดลแก้โจทย์ได้ดีขึ้น เหมือนที่เพิ่ม compute ตอน train ก็ได้โมเดลฉลาดขึ้น ผู้พูดโชว์กราฟว่าทั้งขนาดโมเดลและจำนวน token ที่ใช้คิดดันคะแนนขึ้น และเห็นแนวเดียวกันในหลาย benchmark (Deep Search QA, OSWorld, Humanity's Last Exam)
  2. เดโมสด: prompt เดียว (จำลองรถบนถนนวันเวย์กับไฟจราจร) รันบน Opus 4.7 ที่ low, high และ max effort พบว่า low ใช้ราว 50 วินาที ราว 4,600 output token ได้ผลพอใช้ high ใช้เวลาและ token ราวสองเท่า ละเอียดขึ้น (มีรถหลายแบบ ไฟจราจรเหนือถนน) ส่วน max ใช้ราว 10 เท่า ละเอียดที่สุด
  3. ผู้พูดอ้างกราฟ METR ว่างานที่โมเดลทำได้ยาวขึ้นตามรุ่น และ Mythos ทำงานเทียบเท่ามนุษย์ราว 16 ชั่วโมงที่ความแม่นยำ 50% (ตามที่ผู้พูดบอก)
  4. compute ตอนรันมี 3 ช่อง: thinking (scratch pad), tool calling (ช่องทางกับโลกภายนอก เช่น web search, MCP, เขียนไฟล์) และ text (ข้อความ/คำถามกลับที่ตอบผู้ใช้) ผู้ใช้คุมได้ด้วย effort (dial จาก low ถึง max) และ budget (เช่น max token หรือ task budgets ใน API)
  5. วิวัฒนาการ: คิดก่อนแล้วค่อย tool call หลายครั้ง -> interleaved thinking (คิดหลังทุก tool call) -> adaptive thinking ที่ให้โมเดลเลือกเองว่าจะคิด เรียก tool หรือเขียน text ตอนไหน หรือไม่คิดเลยก็ได้ ผู้พูดบอกว่ามันไม่ใช่ model router และ benchmark ทั้งหมดรันบน adaptive thinking ซึ่ง Pareto efficient กว่า interleaved
  6. thinking toggle เป็นตัวแทนของ effort ที่แย่ เพราะการปิดคือการถอด capability หนึ่งใน 3 อย่างของ Claude ออก ควรให้ Claude รู้ว่ามีเครื่องมือคิดแล้วตัดสินเองเหมือนที่ให้ search tool แล้วให้เลือกว่าจะค้นเมื่อไร
  7. แนวปฏิบัติ: วัดด้วย eval ที่ยากและตรงงานจริง สังเกต diminishing returns (max ใช้ token ราวสองเท่าของ extra high แต่ดีขึ้นนิดเดียวในกราฟตัวอย่าง) และ low เหมาะงานที่ไม่ติดที่ความฉลาด เช่น classification, summarization, data extraction
  8. rule of thumb: max เมื่อรู้ว่างานยากจริง, extra high เป็นค่า default ของ Claude Code และ claude.ai (สมดุลดีสุดตามผู้พูด), high ถ้างานต้องการความฉลาดอยู่บ้าง, medium/low เพื่อลด token และ latency ตัวอย่างเสริม: Claude Plays Pokémon ที่ low effort Claude ใช้วิธีเลี่ยงการสู้ (repel, potion, escape rope) จนจบเร็วขึ้น
  9. โมเดลเล็ก effort สูง หรือโมเดลใหญ่ effort ต่ำ: เทียบ Opus กับ Haiku 4.5 บนโจทย์จำลองรถ Haiku ใช้เวลาครึ่งเดียวแต่ใช้ token เท่ากัน และผลแย่กว่ามาก ผู้พูดสรุปว่าถ้างานต้องการความฉลาดแม้นิดเดียว ใช้โมเดลใหญ่แม้ตั้ง effort ต่ำก็ดีกว่า โมเดลเล็กเหมาะงานง่ายที่ผลลัพธ์ไม่ซับซ้อน ส่วนอนาคตอยากให้ผู้ใช้กำหนดงบ/เวลา แล้ว Claude จัดสรร compute เอง

ลำดับขั้นที่ทำในคลิป

  1. เดโม: รัน prompt จำลองรถบนถนนวันเวย์กับไฟจราจรบน Opus 4.7 ที่ low effort แล้วดูเวลา/token/ผล
  2. รันซ้ำที่ high effort แล้วเทียบ: เวลา token สองเท่า ผลละเอียดขึ้น
  3. รันที่ max effort: ราว 10 เท่า ผลละเอียดที่สุด
  4. เทียบกับ Haiku 4.5 บน prompt เดิม: เวลาครึ่งเดียว token เท่ากัน ผลด้อยกว่า

ตัวเลข / ข้อเท็จจริงที่ผู้พูดบอก

ตามที่ผู้พูดอ้างในคลิป ไม่ได้ยืนยันกับแหล่งอื่น

  • เดโม low effort บน Opus 4.7: ราว 50 วินาที และราว 4,600 output token
  • high effort ใช้เวลาและ token ราวสองเท่าของ low; max ใช้ราว 10 เท่า (ตามที่ผู้พูดบอกในเดโม)
  • กราฟ internal agentic coding benchmark: โมเดลใหญ่สุดได้ประมาณต่ำกว่า 80% (ผู้พูดอ้างลอยๆ จากกราฟ)
  • Mythos: งานเทียบเท่ามนุษย์ราว 16 ชั่วโมงที่ความแม่นยำ 50% บนกราฟ METR (ตามที่ผู้พูดบอก)
  • ค่า default ของ Claude Code และ claude.ai คือ effort extra high (ตามที่ผู้พูดบอก)
  • effort level ที่กล่าวถึง: low, medium, high, extra high, max
  • Haiku 4.5 ใช้เวลาประมาณครึ่งหนึ่งของ Opus แต่ใช้ token เท่ากันในโจทย์จำลองรถ

“Adaptive thinking isn't a model router.”

adaptive thinking ไม่ใช่ตัว route ไปหาโมเดล

“a thinking toggle is actually a poor proxy for the amount of effort that a model should put in.”

สวิตช์เปิดปิด thinking เป็นตัวแทนที่แย่ของระดับความพยายามที่โมเดลควรใช้

“And then finally, when in doubt, go with extra high.”

สุดท้าย ถ้าไม่แน่ใจ ให้ใช้ extra high

สิ่งที่นำไปทำต่อ

  • เปิด thinking (adaptive) ไว้เป็น default แล้วควบคุมต้นทุนด้วย effort ไม่ใช่ปิด thinking
  • สร้าง eval ที่ยากและตรงงานจริง แล้วทดสอบหลาย effort level เพื่อหาจุดที่ผลลัพธ์เริ่มไม่คุ้ม
  • ถ้ายังไม่มี eval เริ่มที่ extra high; ลดเป็น high/medium/low สำหรับงานเน้น latency เช่น classification, summarization, extraction
  • ถ้างานต้องการความฉลาดแม้เพียงเล็กน้อย เลือกโมเดลใหญ่ effort ต่ำก่อนโมเดลเล็ก effort สูง
  • สำหรับงานยาว ให้ลองใช้ budget (max tokens / task budgets) เพื่อคุมต้นทุน

ข้อควรระวังในสรุปนี้

  • ชื่อผู้พูดสะกดตาม ASR ('Alexander Briken') ไม่แน่ใจนามสกุล
  • ตัวเลขเดโม (50 วินาที, 4,600 token, 2x, 10x) เป็นตัวเลขที่ผู้พูดอ่านจากหน้าจอ ผมไม่ได้เห็นภาพ
  • ไม่ได้ยินชัดว่า 'extra high' กับ 'max' ต่างกันกี่เท่า ผู้พูดพูดว่า max ใช้ token 'double the amount' ของ extra high ในกราฟตัวอย่างเท่านั้น
  • ชื่อโมเดล 'Mythos' และ 'Opus 47' มาจาก ASR สะกดเดาว่า Opus 4.7
  • ท่อน 'Deep Search QA' อาจเป็นชื่อ benchmark ที่ ASR เขียนเพี้ยน ('Deep Search QA')
  • ข้ออ้างว่า adaptive thinking Pareto efficient กว่า interleaved เป็นของผู้พูด ไม่มีตัวเลขใน transcript
