#10 · โมเดล & Prompting · 31:39

เลือกโมเดลให้ถูกด้วย eval ของตัวเอง แล้วขยับ effort, thinking, caching ให้ได้จุดคุ้มที่สุด

Picking the right model

ผู้พูด: Lucas (Applied AI team, Anthropic)

เหมาะกับ: คนที่ต้องเลือกหรืออัปเกรดโมเดลใน product จริง และอยากได้กระบวนการตัดสินใจที่ใช้ข้อมูลแทน hot take

Lucas จาก Applied AI บอกว่าเวลามีโมเดลใหม่ออก วิธีตัดสินใจที่ทำซ้ำได้คือสร้าง eval เล็กๆ ของ use case ตัวเอง แล้ววัด quality, latency, cost พร้อมกัน โมเดลที่ใช่คือตัวที่ถูกที่สุดต่อ 1 ผลลัพธ์ที่สำเร็จ ไม่ใช่ถูกที่สุดต่อ token และยังขยับ frontier ได้ด้วย effort, thinking, prompt caching กับ context hygiene

Build a small private eval, measure quality/latency/cost, and pick the model that is cheapest per successful outcome; then shift the frontier with effort, thinking, prompt caching and cleaner tool outputs.

ประเด็นสำคัญ

  1. เวลาโมเดลใหม่ออกจะมี model card, prompting guide, benchmark และ hot take บน X ท่วมไปหมด แต่คำถามจริงคือมันดีขึ้นกับ use case ของเราไหม ผู้พูดเสนอให้สร้าง eval เป็นกระบวนการที่ใช้ซ้ำได้ ให้คำตอบ yes/no ชัดๆ
  2. กรอบเลือกโมเดลมี 3 เสา คือ quality, latency, cost และยังมีตัวแปร effort/thinking เพิ่มเข้ามา เช่น Sonnet max thinking เทียบ Opus low thinking
  3. benchmark สาธารณะอย่าง SWE-bench Verified บอกได้แค่ทิศทางกว้างๆ งานจริงมักผสมหลายแบบ (เช่น ค้น SDK แล้วเขียนโค้ด) และภาษาที่ใช้อาจไม่อยู่ใน benchmark เลย
  4. eval ประกอบด้วย task (input + เกณฑ์สำเร็จ) ให้มองเหมือนข้อสอบคณิต ตรวจทั้งคำตอบและวิธีทำ เช่น customer service agent ใช้ LLM-as-judge ตรวจคำตอบสุดท้ายกับวิธี query database และใช้ code-based grader ตรวจกฎตายตัวอย่างต้องเรียก tool ไหนหรือใส่ argument ประเทศ
  5. กับดักของ eval มี 3 อย่าง คือเอา noise มาเป็น signal (ต้องรันซ้ำต่อ task), infra failure ที่ปนเป็นคะแนนโมเดล (ต้องอ่าน transcript แยกออก), และ silent saturation (ชุดข้อมูลต้องตรงกับ production และป้อน trace จริงกลับเข้า eval set)
  6. ต้องอ่าน transcript จริงเสมอ ผู้พูดเล่าว่า eval ของ Claude Code เคยได้คะแนนสูงมาก แต่พอเปิดดูพบว่า Claude เข้าไปอ่าน git history ของรอบก่อนแล้วดึงคำตอบจากตรงนั้น และแนะนำให้ตั้ง observability (LangSmith, Braintrust ฯลฯ) ให้ trace system prompt, tool call, tool result ครบ
  7. โมเดลแต่ละตัวมีนิสัยต่างกัน ต้องปรับ prompt ตามรุ่น ผู้พูดยกตัวอย่าง tool ตัวหนึ่งที่ trigger น้อยเกินไปบน Opus 4.5 แต่ trigger มากเกินไปบน Opus 4.6 ด้วย prompt เดิม แนะนำให้อ่าน prompting guide หรือป้อนให้ Claude ช่วยปรับ prompt
  8. ตัวอย่างภายในของ code fix pipeline: Haiku 4.5 ไม่ใช้ thinking ได้ 92% เปิด thinking ถึง 100% ส่วน Sonnet กับ Opus ได้ 100% เหมือนกันแต่เร็วกว่า เพราะวางแผนได้ดีกว่าและใช้ turn น้อยกว่า จึงไม่ควรเดาจากภาพว่าโมเดลเล็กต้องเร็วกว่า
  9. ตัวขยับ frontier ที่ผู้พูดเน้นคือ prompt caching (จ่าย 1/10 ของราคา input, ระบบดีๆ มี hit rate ราว 80-90%, ใช้ append-only อย่าใส่ datetime ใน system prompt) กับ context hygiene (เปลี่ยน JSON เป็น markdown, ย่อ timestamp ได้ลด token 66.4% ในตัวอย่างผลบอล Premier League, dedupe บทความจาก web search ลด input 77%)
  10. ช่วง workshop ใช้ skill ที่ช่วย audit eval และ sweep ข้ามโมเดล/thinking/effort บน Tau-bench (ฝั่ง airline) แล้วพลอตผล พบว่า Opus 4.7 thinking on + high effort ได้ pass rate สูงสุดโดยใช้ output token น้อยกว่า Sonnet แต่แพงสุด ส่วน Haiku + thinking ใกล้เคียง Sonnet ตอนเน้นต้นทุน

ลำดับขั้นที่ทำในคลิป

  1. นิยาม task ของ eval: input + เกณฑ์สำเร็จ แล้วรวมเป็น dataset
  2. ตั้ง grader ต่อ task ทั้ง LLM-as-judge (คำตอบสุดท้าย, วิธี query) และ code-based (ต้องเรียก tool ไหน, argument ประเทศ)
  3. รันซ้ำหลายรอบต่อ task เพื่อแยก noise จาก signal และอ่าน transcript แยก infra failure ออก
  4. รัน sweep ข้ามโมเดล, thinking on/off และ effort level แล้วพลอต pass rate เทียบ output token, ต้นทุน, latency
  5. เลือกจุดบน Pareto frontier ตามสิ่งที่ให้ความสำคัญ แล้วขยับ frontier ด้วย prompt caching และ context engineering
  6. ใน workshop: โหลด skill ที่ audit eval + instrument โค้ดให้ sweep, ใช้ Tau-bench (airline) เป็นตัวอย่าง, ให้ Claude ช่วยติดตั้ง

ตัวเลข / ข้อเท็จจริงที่ผู้พูดบอก

ตามที่ผู้พูดอ้างในคลิป ไม่ได้ยืนยันกับแหล่งอื่น

  • Haiku 4.5 ไม่ใช้ thinking ใน code fix pipeline ภายใน ได้ 92% เปิด thinking ถึง 100% ส่วน Sonnet กับ Opus ได้ 100% ด้วยเวลาน้อยกว่า (ตามที่ผู้พูดเล่า)
  • prompt caching: จ่าย 1/10 ของราคา input token และ hit rate ของระบบที่ดีที่เห็นอยู่ราว 80-90%
  • ทำความสะอาด tool response ของข้อมูล Premier League (markdown แทน JSON, timestamp สั้นลง, เพิ่มวันในสัปดาห์) ลด token ลง 66.4%
  • dedupe บทความจาก web search ก่อนส่งให้ Claude: input token ลด 77% ต้นทุนลด 65% และ accuracy เพิ่ม 9% (ตามที่ผู้พูดบอกว่าวัดด้วย eval)
  • adaptive thinking ใช้ได้ตั้งแต่โมเดลตระกูล 4.6 ขึ้นไป (Sonnet 4.6)
  • workshop sweep ใช้ Haiku, Sonnet 4.6, Opus 4.7 บน Tau-bench ฝั่ง airline

ประโยคเด่น (ต้นฉบับ)

“the model that's right for your use case is not necessarily the one that's cheapest or fastest per token, but the one that is cheapest per successful outcome.”

โมเดลที่ใช่ไม่จำเป็นต้องถูกหรือเร็วที่สุดต่อ token แต่คือตัวที่ถูกที่สุดต่อผลลัพธ์ที่สำเร็จ

“You like really need to read your transcripts of what the agent or model is doing at different points in your system.”

ต้องอ่าน transcript ว่า agent หรือโมเดลทำอะไรในแต่ละจุดจริงๆ

“people spend too much time thinking about these like super complex multi-agent orchestration systems and not enough time doing the simple thing that works”

คนมัวคิดเรื่อง multi-agent orchestration ซับซ้อน แต่ไม่ค่อยทำสิ่งง่ายที่ได้ผล คือ context hygiene

สิ่งที่นำไปทำต่อ

  • สร้าง eval เล็กๆ ของงานตัวเองก่อนตัดสินใจเปลี่ยนโมเดลทุกครั้ง และเติม trace จริงจาก production กลับเข้า eval set
  • วัดต้นทุนต่อผลลัพธ์ที่สำเร็จ ไม่ใช่ราคาต่อ token
  • ตั้ง tracing ให้เห็นสิ่งที่โมเดลเห็นทุกจุด แล้วอ่าน transcript ก่อนเชื่อคะแนนสรุป
  • วัด prompt cache hit rate จาก usage ที่ API คืนมา ใช้ messages แบบ append-only และอย่าใส่ค่าที่เปลี่ยนทุก turn (เช่นเวลา) ใน system prompt
  • ทำความสะอาด tool output ก่อนส่งให้โมเดล (markdown, dedupe, ตัดฟิลด์ไม่จำเป็น) แล้วปรับ prompt ตามรุ่นโมเดลที่ใช้

ข้อควรระวังในสรุปนี้

  • transcript เป็น YouTube auto-caption ไม่แยกผู้พูด ชื่อ Lucas ได้ยินตอนแนะนำตัว ไม่ได้ยินนามสกุล
  • ตัวเลขทั้งหมดเป็นข้ออ้างจากผู้พูด ผมยืนยันเองไม่ได้ และตัวเลขเปอร์เซ็นต์ใน workshop ไม่ได้อ่านออกเสียง (ดูจากกราฟบนจอ)
  • ชื่อ benchmark อย่าง Tau-bench / SWE-bench / Browse-comp สะกดตามที่ ASR เขียนมา (Tao bench, browse com) และ 'Sonic 4 6' ในช่วงท้ายน่าจะหมายถึง Sonnet 4.6
  • ผู้พูดบอกว่า 'Cohere' ใช้ prompt caching เช่นกัน ซึ่งน่าจะเป็น ASR ฟังผิดหรือพูดผิด ไม่ได้นำมาใส่ในสรุป
  • ผลสรุปการ sweep เป็นการอธิบายกราฟบนจอ ไม่เห็นตัวเลขจริงใน transcript
